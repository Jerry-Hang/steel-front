# DLSS 立项评估（2026-09-25）

> 未结案 #20 的最后一个子项。结论**不建议现在接**，理由与"什么条件下重新评估"写在下面。
> 本文只引用本仓自己量过的数字，不外推 NVIDIA 的市场材料。

## 1. 结论（TL;DR）

| 问题 | 答案 |
|---|---|
| 硬件支持吗？ | 支持。启动日志里 `VK_NVX_image_view_handle = true`、`VK_NVX_binary_import = true`（`engine/gpu_caps.rs` 已在探测并在结论行里报"可直接接 DLSS SDK"） |
| 引擎现在能接吗？ | **不能直接接**：缺三样 DLSS 必需输入 —— **逐像素运动矢量**、**投影 jitter**、**深度/线性深度暴露**；而且 HUD 与主 pass 共用 MSAA 4x 管线，合成顺序要改 |
| 值得接吗？ | **现阶段不值得**：DLSS 省的是**像素**成本，而本仓实测是**顶点瓶颈** —— 像素面积减到 1/4 只换来 **+12%** fps；同时它要新增 NGX SDK（违反"不新增第三方依赖"硬约束，需用户明确同意） |
| 什么时候再看？ | 当"把内部分辨率降 4 倍"的 fps 提升 **> 40%**（即像素成本成为主项）时，或出现 4K+ 高画质/大量透明特效这类真实需求时 |

## 2. 本仓关于"成本在哪"的既有实测（这是评估的支点）

来源：`docs/PROGRESS.md` 第 39 轮性能定位 + 道具焊接那一轮的对照实验，以及铁律 D 的结论行。

| 实验 | 结果 | 说明 |
|---|---|---|
| 每帧提交盘点 | 24.3 万三角形 / **58 万顶点** / 28 draw call ⇒ GPU **3.7ms** | 157M 顶点/s、66M 三角形/s，对 RTX 5060 是很小的量 |
| 填充率（分辨率） | **像素面积减到 1/4 只 +12% fps** | ⇒ 像素成本不是主项 |
| 一次画完（少 draw call） | **−38% fps** | ⇒ draw call 也不是主项，甚至不是单调的 |
| 顶点数（道具焊接） | 156 万 → 51 万顶点：**中位帧率 +18.6%** | ⇒ **顶点数才是本仓的帧率杠杆** |

**⇒ DLSS 的作用面（像素着色 + 时间重建）正好落在本仓最不痛的地方。**

另外两点让 DLSS 的收益进一步缩水：

- 本仓**纯平着色**（顶点格式 `stride=32`，`pos/color/uv`，**没有法线槽位**），
  没有法线贴图、没有复杂 PBR/次表面/半透明 —— DLSS 的"省着色"红利在这里基本不存在；
- 画面主体是**大量高频薄几何**（instanced 城市板楼 + 破损），DLSS 的典型副作用
  （薄物体拖影 / 亚像素闪烁）恰恰在这种内容上最明显，验收成本高。

## 3. 要接的话，缺什么（成本清单）

| # | 缺的东西 | 现状 | 工作量估计 |
|---|---|---|---|
| 1 | **逐像素运动矢量** | **完全没有**（`rg 'motion_vector' src/` 无命中）。要为地形实例场、marker、NPC、道具、枪模分别产出一份，含相机运动 + 物体运动 + 动态物体（NPC/尸体/弹丸） | **最大的一块**，等于给渲染器加一条 GBuffer 通道 |
| 2 | **投影 jitter** | 无。需要每帧子像素偏移并让所有几何用同一 jitter 矩阵（`main.rs` 的 `proj` + `build.rs` 的着色器 push constant） | 中等，但**牵一发动全身**（HUD、枪模、PT 都吃同一个投影） |
| 3 | **深度/线性深度暴露** | 深度只用于主 pass 的深度测试，没有给后处理用的采样路径 | 中等（要新增深度采样 + 布局转换） |
| 4 | **合成顺序** | HUD 与主 pass 共用 `hud_pipeline`（MSAA 4x + 带深度）；DLSS 必须在 HUD **之前** upscale | 中等（拆分后处理链） |
| 5 | **NGX SDK 集成** | 未引入 | 新依赖：native lib + 运行时 DLL 分发 + 初始化/每帧 evaluate + 失败回退 |
| 6 | **验收手段** | DLSS 的鬼影/拖影要看**动态画面**，而本仓截图通道在独显上本来就不稳（§21.4/§21.8） | 高：需要视频/连拍对比基线 |

## 4. 决定与替代路线

**现在不接 DLSS**，把同样的工程量投到已经被本仓数字证明的地方：

1. **顶点侧**（收益最确定）：道具焊接（已 +18.6%）、实例剔除、mesh shader 分流、地形 LOD；
2. **呈现/同步侧**（2026-09-25 刚做的三处）：等待全部有界（`u64::MAX` → 静默僵死的根因）、
   acquire 超时降级 mailbox、`gpu_stalled` 后保持进程响应；
3. 若将来真要"高分辨率 + 高画质"，先做**零依赖**的候选：
   - 分辨率缩放（内部渲染低分辨率 + 简单上采样）—— 本仓已有 `RESOLUTIONS` 与 `RV3D_NO_*` 开关，
     可以先用它量出"像素成本占比"这条判据线（**> 40% 才回头谈 DLSS**）；
   - 更高杠杆的几何优化（顶点数、实例数、LOD 档位）。

## 5. 重新评估的触发条件（写成可判定的判据）

任一条成立就重开这个议题：

- **判据 A**：把内部分辨率降到 1/4 像素面积，fps 提升 **> 40%**（说明像素成了主项）；
- **判据 B**：新增了重像素特性（体积雾 / 大量半透明 / 屏幕空间反射 / 复杂 PBR），
  且它们单独占帧时间 **> 30%**；
- **判据 C**：用户明确接受新增第三方依赖（NGX SDK）并把它列为版本目标。

**在此之前，看到"再加个 DLSS 就快了"的提议，先回答：本仓像素成本只值 12%。**
