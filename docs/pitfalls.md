### 0.2 十个反复出现的根因母题

按证据量排序（括号内 = 在 162 条里的命中条数，由关键词统计得出）。

#### ① 同一事实有多份副本，改动只落在其中一处（同源，19 条）

同一个约定被写了两遍：**光栅 vs PT**、**mesh 路径 vs 顶点路径**、**生产者 vs 消费者**、
**着色器声明 vs 描述符布局 vs 写入函数 vs 池计数**、**CPU 立方体 vs mesh 圆柱盖**。

典型：`pt_set_scene_markers` 的 `* 0.5` 是"渲染盒 = 2×AABB"时代的正确写法，
9-17 改了**生产者**（可见尺寸 = AABB）却漏改这个**消费者** ⇒ PT 的 marker 盒整体小一半，
而唯一"对"的圆柱 Y 是**恰巧蒙对的**（模板半幅正好 0.5）。
另一例：光栅加了 `!is_canopy` 排除、PT 侧一直有、注释还声称"与光栅逐条同式"。

⇒ **教训**：改一条规则前，先列出它的**所有消费者**；两侧实现要有**同源判据**（同一个常量/函数），
不是两边各写一份公式再在注释里声称一致。

#### ② 判据取自被测物自身 ⇒ 同源同错，过期不可见（判据骗人，42 条里最核心的一类）

- **表与清单互相对齐**：表是生成物、清单也是生成物 ⇒ 两者一起停在 1580，
  而源码实际用了 **1591** 个 CJK 码点。判据永远绿。**这件**是"扫描面为 0 也算通过"的变体。
- **旧的合并测试按臆想的顶点布局断言"逐位相同"** ⇒ 把"tint 乘在 uv 通道上"这个 bug **固化成了回归守卫**。
- **恒真的断言等于没写**（`npcs.len() >= 0`）。

⇒ **教训**：判据必须**独立重扫真源**。凡"两份生成物互相对齐"的断言，
先问它**扫到 0 个时会说什么**。

#### ③ 未知输入取一个"看起来合理"的默认值（9 条，且后果最隐蔽）

glTF 解析器是重灾区：未知 `componentType` 按 4 字节浮点读、
`count` 缺失 `unwrap_or(0.0)`、`normalized` 完全不换算、不支持 `byteStride` ⇒ 交错缓冲读成乱麻。
**要害在于**：4 字节整数当 `f32` 读出来**仍然是合法浮点数** ⇒ 不崩、不报错，只是几何悄悄变形。

同族：`[rule]` 键缺失走 `unwrap_or(0)` ⇒ `targets=30` 手滑写成 `target=30` 时
`kills >= 0` **恒真** ⇒ **开局即胜利**。

⇒ **教训**：必填字段缺失、未知枚举一律 `Err` 并点出字段名与实际值；
`_` 分支不许留默认值。**"有兜底"不是不报错的理由，恰恰相反。**

#### ④ 写死的值被默认配置掩护（13 条）

PT 上屏 blit 的目标范围写死 `2560x1600`，而**默认窗口就是 2560x1600** ⇒
此前每一轮 PT 验证都躲过去了；换尺寸那一帧直接 `VUID-vkCmdBlitImage-dstOffset-00248` + 设备丢失。
同族：窗口尺寸请求写死 DPI 1.5（Windows 那台的 `scale_factor`）⇒ Linux 上分辨率整体失真，
而**日志照样打印"窗口创建成功: 2560x1600"**（打印的是请求值，不是生效值）。

⇒ **教训**：验证**必须覆盖非默认配置**；日志必须打印**实际生效**的值。

#### ⑤ 平台的某条分支在另一平台永远走不到（11 条）

`VkSurfaceCapabilitiesKHR::currentExtent` 在 **Wayland 下设计上就是未定义的**
（Mesa 填 `UINT32_MAX`），而 Win32/X11 下它恒等于窗口尺寸 ⇒
**那条兜底分支在 Windows 上永远不被执行**，兜底值从没被验证过。
同族：`DeviceEvent::MouseMotion` 在 Windows 上**根本不存在**（winit 只构造 `Added`/`Removed`），
而代码那条 `Locked` 路径**为 XInput2 而写**，迁到 Windows 后前提消失、代码没跟着改。

⇒ **教训**：平台差异要当成一张「**哪条分支在另一个平台上永远走不到**」的清单来管；
把「平台会不会投递某事件」当**假设去验证**，不是当事实。

#### ⑥ 失败路径没有统一形状（`if let Ok` / `let _` / 先销毁再创建）

- `if let Ok(..)` 吞掉上传失败 ⇒ **计数照设、缓冲没写** ⇒ draw call 按新计数读未初始化显存；
  而"士兵索引一个都没写进去"这件事**不报任何错**。
- 6 处 `let _ = device_wait_idle()` 让「等待成功」与「等待失败」在日志里**一模一样**，
  而它最可能返回的正是 `VK_ERROR_DEVICE_LOST` —— 本仓最贵的一类故障。
- `set_props` **先 unmap/destroy 旧的再 create** ⇒ create 失败时字段里留着**已销毁却非 null** 的句柄。

⇒ **教训**：上传一律「**先建新的 → 映射成功 → 才拆旧的 → 换句柄**」；失败只降级；
`destroy` 之后**立刻把字段置 null**。

#### ⑦ 两个错误互相抵消，所以现象自洽（5 条 + "巧合" 2 条）

`for_obstacle` 对三轴一律写 `2*half`，而模板是 ±1 立方体/球 ⇒ **渲染尺寸是设计尺寸的 2 倍**；
更要命的是弹孔路径一直靠 `visual_half_gain = 2.0` **补偿同一个 2 倍** ⇒
**两边同时错，所以自洽**，路缘石 0.55m 画成 1.1m 矮墙也没人觉得不对。

⇒ **教训**：**凡发现自己写的补偿因子恰好等于另一个错误，先去找那个错误，不要留着它。**
半幅只能有一个真源（`template_half_extent`）。

#### ⑧ 容量触顶静默丢弃（7 条）

`if len < MAX { push }` / `boxes.len().min(PT_MAX_BOXES)` / `quads.len().min(capacity)`
三处都**只丢弃不吭声**。PT 实测 547 > 512 ⇒ **每次静默丢 35 个盒子**，
而低 spp 的噪点图**肉眼看不出来**。

⇒ **教训**：每个截断点配一个**一次性告警闩**，并且要能报出「**容量 vs 实测峰值**」，
让下次调容量有依据。

#### ⑨ "没跑成"被当成"跑过了"（10 条）

`vuid == 0` 在**验证层没开**时是**结构性恒真**（日志里根本没有 VUID 字样）；
`survive_pm` 的判据**整整读了一份空文件**却打 ALL-OK；
闸门在**非仓库目录**跑并打"没有命中"。

⇒ **教训**：审计/闸门工具必须有**第三种结局**「没跑成」，约定
**0 = 真扫过无命中 / 1 = 有命中 / 2 = 根本没扫成**。
（这条已经是本仓的铁律，但它被**反复**违反 —— 见 `lying-gates.md` 全档。）

#### ⑩ "工具跑不起来"被写成"已知限制"（工具/环境档的核心）

`RV3D_VALIDATION=1` 曾因 mesh.spv 过不了严格 spirv-val 而**灰屏** ⇒
这条通道长期"文档里写着但没人用"。**把它修好、第一次真跑起来，立刻报出两条一直存在、
此前完全不可见的 VUID**，PT 也才第一次真正出图。

⇒ **教训**：**「工具跑不起来」本身就是一条要修的缺陷**；
任何"工具用不了"都要当场问根因，**修好后的第一个动作就是重跑它**；
把"工具坏了"写进文档时，必须同时写「**这期间哪些判据不适用**」。

### 0.3 最值钱的一类：误判的方向

162 条里有 6 条明确写了「**当时以为是 X，其实是 Y**」。这类信息比错误本身更有价值，
因为它记录了**推理是怎么走偏的**：

| 当时以为 | 实际是 |
|---|---|
| 建筑模型坏了（"乱窗/透视错误"） | `pick_building` 缩放取 `max` ⇒ 全城 52 处楼互相穿插 |
| PT 的 bug | `hud_framebuffer` 指向**已销毁的 ImageView**，而它的唯一消费者就是 PT |
| 光照/阴影/贴图有问题（"三重排除"全做完了） | 片元引用了一个**布局里不存在的 binding**，未绑定描述符**恒采样 0**，被乘性分支乘成纯黑 |
| 几何画错了（"两根电线杆"） | 平放薄圆盘从人眼高度几乎投影成一条线 —— **视角依赖的可见性** |
| 参数还不够极端（改了没效果） | 屏幕上那个塔**不是这个生成器产的** |
| 透视错觉 / 相机位置不对（"广场上一个坑"） | 几何本身有空腔，低机位下内壁立面就是一道"往下掉的墙" |

⇒ **可复用的动作**：断言"某物没渲染/画错了"之前，
**先确认相机在它的正面、它有面向相机的投影面积、且屏幕上的东西确实是这段代码产的**
（grep 特征常量列出所有发射者）。本仓教训 3/41 说的就是这件事。

## 1. 怎么用这份文档

## 3. 附录：这份盘点是怎么来的（可复现）

```bash
# 1) 抽语料：全部 fix 提交的正文，按 scope 分组
#    （本仓提交正文很详细，通常写清症状/根因/判据 —— 所以语料本身就是一手材料）
git log --reverse --format='%h%x1f%ad%x1f%s%x1f%b%x1e' --date=short HEAD > /tmp/raw.txt

# 2) 按 scope 分节写成 /tmp/fixcorpus.md（约 307 KB / 283 条）

# 3) 用并行分身按 scope 分 7 片提取，**各自写文件**、只回一行摘要
#    ⚠️ 这里有个坑：第一版让分身把正文"返回"，163 条正文 60+ KB 必然溢出，
#       落盘文件也被截断在 5 万字符 ⇒ 数据丢了。**让分身写文件、只回摘要**才是对的。
```

**复核方式**：`docs/pitfalls/` 下 7 个文件的条目数合计应为 **162**；
每条的「来源模块」标明它出自哪一片（渲染/几何/输入/逻辑/联网/工具/平台）。

## 4. 最后的提醒

这份文档**不是**"以后不会犯这些错"的保证。162 条里有相当一部分是**同一形态在不同地方重演**：
「同源违反」在渲染、几何、输入、工具里各出现了一次；
「判据骗人」在 42 条里几乎每一条的写法都不同。

真正可迁移的只有一条：

> 🔴 **任何量化/自动化的结论之前，先问「我的测量工具测的是我以为的东西吗」，
> 再问「它失败/扫到 0 个的时候会说什么」。**

本仓为此栽过的次数，是这份文档存在的全部理由。
