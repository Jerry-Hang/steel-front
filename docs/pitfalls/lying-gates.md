# 判据骗人 —— 误区与陷阱（42 条）

> 测试/闸门/探针自己失效：恒真、扫描面为 0、只匹配到注释
>
> 返回 [`docs/pitfalls.md`](../pitfalls.md)（总索引与全局综述）。
> 每条格式：**症状 → 根因 → 教训 → 类别**。根因里保留了「当时以为是什么」——那是最值钱的部分。

## 判1. 判据自己的三种骗法：空测量、不能失败的门槛、就地取用被测代码的输出

- **症状**：① 改动的区域对比里"必须变"的帐篷也是 0.00% 变化；另一版 VVL 计数器报 `distinct VUIDs: 0`，而日志里明明有 VUID。② 给树冠改动设的"改后应≈0"门槛拍成 5%，对任意两帧只会印 FAIL。③ 一个 1.5m 的尺寸门限被写成 `2.0*max(2*hw,…)`，门槛悄悄变 0.75m、只拦 264 件，靠新测试当场红才抓到。（5c8703b, 2026-10-02；a94496f, 2026-10-01；8548ba2, 2026-09-29）
- **根因**：① 相机在帐篷正上方，它根本不在框里 ⇒ "全 0"是"没测到"不是"没变化"；正则写成 `VUID-[...]` 匹配不到真 VUID ⇒ 报 0 是结构性恒真。② 门槛不是从现象反推的，拍脑袋定的门槛对任何输入都只会失败——一个不会失败的判据等于没有判据（反过来永远失败的判据同样没人看）。③ 断言直接拿自己手推的公式当基准，错在同一个地方就互相印证不了；这次判据是先从独立测量（导出 1789 件逐件量跨度）写进断言，代码一对不上就红。
- **教训**：量化结论前先问"这个判据在'什么都没测到'时会说什么"（"0"不能当成"通过"）；门槛必须能双向失败（改前红、改后绿）并在正对照样本上验一次检测器（正则/扫描器都要有"必须命中"的样本，脚本要按昨天两份基线日志同法校准）；断言里的期望值只能来自独立测量，不能来自被测代码或自己刚推的公式。
- **来源模块**：渲染管线

## 判2. 验证层没开时 `vuid == 0` 是结构性恒真——日志里永远不会有 VUID 字样

- **症状**：冒烟脚本长期打印 `VUID=0 … RESULT: ALL-OK`，看起来每个提交都过了 VUID 判据。（a18011d, 2026-10-08）
- **根因**：验证层（`RV3D_VALIDATION=1`）默认关，不开时日志里根本没有 VUID 字样 ⇒ `vuid == 0` 这个比较恒成立，是"没跑成"被当成了"跑过了"。同形缺陷在别处也出现过：历史密钥审计在非仓库目录打"没有命中"、survive 脚本的判据整整读了一份空文件。
- **教训**：闸门必须有第三种结局——"没跑成"要显式说出来（现在验证层没开时脚本明说「VUID 判据：不适用」，开了则按类型分类：三条已验证噪声打印计数不算失败，**任何未知 VUID 一律 FAIL**）；凡是扫描/模糊/审计类判据，先问"它扫到 0 个时会说什么"，并给检测器加"必须命中一部分"的自检（"没 panic"证明不了任何事）。
- **来源模块**：渲染管线

## 判3. 检查工具自己写错：匹配表漏一项、扫描器只产假阳性、旧测试把错位布局断言成逐位相同

- **症状**：① `no_expect_or_unwrap_on_vulkan_calls` 全绿，而 `init_instance()` 里就有一句 `.create_debug_utils_messenger(...).expect(...)`；② 手写的"被丢掉的 VkResult"扫描器 122 条命中里几乎全是假阳性；③ 把 `placement_tint` 乘进 `v[6..9]` 的 bug 被旧测试按错误布局"逐位相同"地固化了很久。（5d9c569 & 82d096b, 2026-09-26；a1d6c12, 2026-09-19）
- **根因**：① 判据靠一张 `CALLS: [&str; 8]` 的调用名表匹配，`.create_debug_utils_messenger(` 不在表里 ⇒ **判据漏掉一个名字，规则就等于没有**。② `Result` 是 `#[must_use]`，语句位置丢弃本来就会被 `unused_must_use` 顶成警告 ⇒ 这一轴编译器已经在管，文本扫描器没有增量价值；真正的漏洞只有 `let _ =` / `.ok()` 这两个**故意消音**的写法（改由源码判据兜住）。③ 导入器布局实为 `pos(3)nrm(3)uv(2)col(3)`，缩放落在 uv 上、只有 color.r 被染色，而测试按同一个错误布局断言 ⇒ 错误被写进判据。
- **教训**：源码守卫的匹配表要能"必须命中已知样本"（补上那个调用名后判据当场在 renderer.rs:1768 红，缺口才算被证明；同理 `no_if_let_ok` 要只扫代码行，否则注释里的示例会让它自指恒红）；先问"这一轴编译器/类型系统是不是已经管了"，别写只产假阳性的扫描器；把新加资源的"建"和"拆"当成同一步——资源审计工具上线两小时抓的就是当天新加的 5 个未释放资源（`no release call found: 5 → 0`），但它只是 tripwire、不是证明。
- **来源模块**：渲染管线

## 判4. 注释和日志在骗人：`RV3D_PT_SPP` 是"累积帧数"，设小值等于改曝光

- **症状**：照注释"调参/快速预览可设小值"把 PT 设成 16/64 做 A/B，得到一条"PT 曝光随 SPP 变化 +26%"的缺陷结论。（2ae3b2b, 2026-09-29）
- **根因**：`RV3D_PT_SPP` 覆盖的是 `pt_spp_target`（默认 256），单位是**累积帧数**：`accumulating = pt_frame < pt_spp_target` 到数就停止 dispatch、画面冻结；而 glsl 末尾的累积是**指数滑动平均** `acc = mix(acc.rgb, lum, 1/a)`，显示时又按"求和样本数"再除一次 `acc.rgb/acc.a` ⇒ 双重归一化，acc 从 0 起步的暂态被直接显示：按稳态窗口 64 帧估，第 N 帧只到 1−(63/64)^N ⇒ 16 帧 22.3%、64 帧 63.5%、256 帧（默认）98.2%。实测同向同序（全局灰度均值 90.7 vs 114.1，且非线性压缩），默认 256 帧已到 98.2% 所以正常路径看不出来。
- **教训**：注释/日志里的语义也是判据，会直接决定实验怎么设计——凡是"调参旋钮"先读它到底改了哪一行；拿 PT（或任何时域累积图）做定量对照（比亮度/反照率/砖纹对比度）必须用默认 256 帧并写明口径；已经据此产出的结论（"PT 砖周期 +19%"、"+26% 曝光"）在正确口径下重测前，既不能定案为缺陷、也不能定案为测量产物（测量带混入 72 行天空同样是作废理由）。
- **来源模块**：渲染管线

## 判5. 只在默认配置上验证过：写死的像素值躲过每一轮验证，换个尺寸就把设备打掉

- **症状**：PT 上屏 blit 的 `dst_offsets` 末角写死 `x:2560, y:1600`，而默认窗口**就是** 2560x1600 ⇒ 此前每一轮 PT 验证都躲过了它；换 1280x720 的第一帧就 `VUID-vkCmdBlitImage-dstOffset-00248` ×5 并把逻辑设备打掉（VUID 6、`has been lost` 3935 条）。同类：交换链兜底尺寸写死 1280x720；Wayland 下交换链恒 1280x720（`currentExtent` 设计上未定义），投影用窗口尺寸、HUD 按窗口排版却画进 720p。（2828900 & c5f085a, 2026-09-26；b3874af, 2026-09-28；d7b2444, 2026-10-03）
- **根因**：这些分支在 Windows + 默认配置上**永远走不到**（Win32 的 `currentExtent` 恒等于窗口尺寸、默认窗口恰好等于写死的值），于是它们从未被任何一轮红/绿验证覆盖，到 Linux（Wayland / AMD 610M）或缺扩展的设备上才暴露。扩展那条更狠：`enumerate_device_extension_properties` 的结果只在**事后**用来打一行 warn，缺任一光追扩展的后果不是降级而是 `create_device` 失败 = 游戏起不来，而 PT 本来就默认关。
- **教训**：验收必须覆盖非默认配置（换尺寸用 `scripts\run_resize_probe.ps1`，PT 也要各跑一轮）；硬编码像素范围要有源码判据 `blit_regions_never_hardcode_pixel_extents`（非原点 `Offset3D` 不许是纯字面量）——注意该判据的自检当场抓到检测器自己漏放行 `\n`、会对"跨行写死"静默放过；能力类请求要按真实能力筛选并允许降级，成组使用的光追扩展必须**全有或全无**（半套启用是 UB，比整组不用更危险），缺失日志要 info/warn 分明（此前每局都打 warn，真缺失会被噪声淹掉）。
- **来源模块**：渲染管线

## 判6. 垂直镜像翻烧饼：一天之内四轮互相矛盾的"根因"，最后一轮把显式翻转全部撤销

- **症状**：世界/UI 上下颠倒，随后"世界倒立"，再改回来……同一现象在 2026-08-08 与 08-16 反复出现，每轮都宣布找到了根因；其间既有"顶点/HUD/阴影 shader 补显式翻转"，也有"撤销上轮对 vertex/shadow 的多余翻转（双重翻转导致世界倒立）"。最后一轮撤销全部 shader 显式 Y 翻转，以**用户实机画面正常**为判据、364 测试全绿。（f3fced7, 2026-08-08；2486cbd / baa00f1 / 8828181 / b1da9c2, 2026-08-16）
- **根因**：四轮给出的机制各不相同且先后被推翻：先是"naga 30 多成员输出结构不发射 ADJUST_COORDINATE_SPACE 翻转"，接着收窄成"只有网格路径对 vertices 数组内 position 的翻转失效（顶点路径正常）"，再变成"ADJUST_COORDINATE_SPACE 对全部 shader 均为死代码（翻转落在副本变量上）"。**当时每轮都以为是"某个 shader 少翻了一次"，其实是"一共翻了几层、以及哪一层承担翻转"从来没被量过**；语料没有记录最终由哪一层承担翻转。
- **教训**：方向/符号类改动必须先建立可复核的证据（SPIR-V 反汇编 + 像素级验证——第三轮正是靠它确认 ADJUST_COORDINATE_SPACE 是死代码），否则每轮都会推翻上一轮；把约定写成单点契约（翻转只由某一层负责、别处禁止再翻投影）并加判据；最终判据要用实机画面而不是"测试全绿"。
- **来源模块**：渲染管线

## 判7. 围墙"没有豁口"不等于闭合，四个大门被自己的半宽算法填死

- **症状**：实机截图发现四角各一个 22.5m 缺口（玩家能从角上直接走出城市），四个 12m 大门全被墙填死、门柱整根埋在墙里、只有旗杆和灯头从墙头伸出来；而旧测试 `perimeter_has_no_unintended_gaps` 一路绿灯。
- **根因**：7 段 × 55m = 385m 铺不满 430m 墙线，缺口留在首末段之外，而旧测试**只查「相邻段之间有没有豁口」**——段间确实没有；大门分支又把 `(seg - gate) * 0.5` 当成半宽传给 `pw`，每片墙身实宽 43m、两片在中央重叠 9.5m。**「没有豁口」和「闭合」是两件事。**
- **教训**：判据要写成覆盖性断言（"必须铺到 ±CITY_WALL"），并补 `gates_are_passable` 这种"功能性"断言；新判据必须在旧代码下先红（这两条改前实测 FAILED：22.5m 缺口 / 大门被堵死）。
- **来源模块**：城市与几何

## 判8. 纯平着色 + 无法线槽位：同心球读成巨石、近相切交线读成 V 槽、<15cm 板 15m 外消失

- **症状**：灌木先是"绿色巨石"（两团几乎同心的细分球），改成 5 团后**比原来更糟**——外圈半径全小于中心团 ⇒ 交线近乎相切 ⇒ 平着色把每条交线画成深色 V 槽、轮廓挤出三角尖角，实机像揉皱的金属皮；长椅 12cm 座板从正面看只剩悬空靠背和两条腿，读作塌掉的椅子。
- **根因**：本引擎**没有法线槽位 ⇒ 只能纯平着色**，形状语义完全由面片朝向决定，小于 ~15cm 的板在 15m 外就消失。另一处误判同理：所谓"坑里的塌长椅"根本不是长椅，是花坛里 2.9m 棕色土台（四周缩进 0.25m、顶面高出 4cm）的两个侧面 + 顶面在平着色下拼成的——**是我自己多放的一个盒子**。
- **教训**：球组必须保证"球心不高于切平面"（判据 `planter_bushes_are_clean_domed`，旧代码球心 0.76..1.17 红）；家具板厚按"看得见"定、不按木工尺寸定；给地面物件加"材质贴片"式第二层薄盒之前，先问它的侧面会不会在低机位被读成一件独立物体。
- **来源模块**：城市与几何

## 判9. 预渲染审计把"埋没规则线"当地面 ⇒ 所有接触缝被系统性放大 10cm，浮空读数成了假阳

- **症状**：aud2 的"弹珠漂浮 / 整墙浮空"读数——违规本身真实，但**量级是毫米**，被工具放大了 10cm。
- **根因**：`prerender_city.py` 把 -0.05（埋没规则线）当地面，而游戏里可见地面是 +0.05 的平铺 quad ⇒ 一切接触缝被系统性放大 10cm：**是尺子错了**，不是资产错成那样。同一轮还按**直径**误读 icosphere stretch（乘的是半径 0.24），把 bag 改成 2.40 造成包体过宽戳爆声明包围盒，已回退。
- **教训**：审计工具的地面基准必须与被渲染的真实地面同源（-0.05 → +0.05）并写进工具；改正基准后要重新平衡被"过挖"的资产（hesco 0.02→0.05、sandbag 0.08→0.13，找回被过挖的 5cm 设计墙高）；半径/直径这类量纲先看代码里乘的到底是哪个。
- **来源模块**：城市与几何

## 判10. tint 乘错通道（v[6..9] 实为 uv+color）⇒ 克隆军团对策自出生未生效，而旧测试把 bug 固化

- **症状**：`placement_tint`（治"同型号建筑克隆军团"的逐摆放确定性色调）从落地起就没生效——实测只有 color.r 被染色、uv 被缩放。
- **根因**：`merge_binned` 把 tint 乘在 `v[6..9]`，而导入器布局实为 `pos(3) nrm(3) uv(2) col(3)` ⇒ `v[6..9]` 是 uv(2) + col 的前一位。**旧测试按错误布局断言"逐位相同"，把 bug 固化了下来**；这是靠读码抓到的，不是靠测试。
- **教训**：凡"某功能自出生未生效"先查写入偏移与真实顶点布局是否同源；测试断言的布局必须取自唯一真源（导入器布局）——按错误前提写的"逐位相同"断言比没有测试更糟；判据要一次补齐名单/桶三角形数/盒壳绕序/tint 通道四条。
- **来源模块**：城市与几何

## 判11. 焦点判据用框架自己的标志 ⇒ 恒 false，"键盘能用、鼠标转不了视角"

- **症状**：用户实测键盘正常但视角不转；`cam:` 诊断行同时打印 focus/cap/lock 与 CursorMoved 计数，看到 `cap=false` 而键盘事件照收。
- **根因**：先改成问 `has_focus()` 而不只信 `Focused` 事件，但 winit 文档自述 `has_focus()` 与 `Focused` 事件读的是**同一个内部标志** —— 窗口创建时即为前台就不会再发 `WM_SETFOCUS`，于是 `Focused(true)` 永不投递、`self.focused` 恒 `false` ⇒ `want` 恒假 ⇒ 光标永不抓取，连"抓取失败"的告警都没有（因为压根没尝试）。
- **教训**：把"框架状态查询"当独立证据前，先确认它不与该框架的事件同源（读文档/看实现）；跨平台窗口状态落到操作系统级的可比量（`GetForegroundWindow` + 进程 ID 比对），并把 `fgpid/mypid` 打进诊断行，让"焦点判据到底成不成立"在日志里可见（修后实测 `focus=true cap=true lock=false mouse=15`，抓取链路才打通）。
- **来源模块**：输入与交互

## 判12. 安全网把脚本自己标注为 informational only 的量当硬门槛 ⇒ 每次运行都误报 FAILED

- **症状**：`release_input.ps1` 每次运行都报 `RELEASE FAILED`，而实测 `ClipCursor` 已恢复全屏 `0,0-1707,1067`、进程为 0，鼠标确实自由。
- **根因**：判据里混进了"光标可见性"这个不可靠量 —— 脚本自己在该量旁标注了 `thread-scoped, external query unreliable -- informational only`，判据却拿它做门槛。结果真正失效时没人再当回事。
- **教训**：判据只能由**直接测真实失效模式的量**组成（这里是 `alive==0` 且 `clipOk` = 指针没被钉住），不可靠量只许打印作诊断；会喊狼来了的安全网比没有更糟 —— **安全网的假警报和漏报一样有害**，发现误报要当场改判据，而不是教人忽略红字。
- **来源模块**：输入与交互

## 判13. 字模清单与表"两边一致"，所以"清单过期"这件事测试永远发现不了

- **症状**：源码实际用了 1591 个 CJK 码点，而点阵表与清单都停在 1580 —— 两边一致，所以那条测试一直是绿的，过期完全看不出来；多出的 11 个字全部来自新写的**注释**，屏幕上看不出任何异常（下次落到真正会渲染的字符串上，症状就是"HUD 上少一个字的空白"，而那时离根因已隔了一次手动生成）。
- **根因**：判据取自清单，而清单本身是生成物 ⇒ "表与清单一致"是个恒真式，扫描面与真实使用面脱钩。起因只是想审计"还有谁把 SimSun 当现行字体"（模块头改了、生成物头没改），追下去发现真问题不在措辞，在**清单会过期而没有任何东西发现**。

## 判37. 致命启动错误以退出码 0 收场，调用方把「一帧都没渲染」当成「跑完了」

- **症状**：在没有图形会话变量的 shell 里（XDG_SESSION_TYPE=tty，缺 WAYLAND_DISPLAY/DISPLAY）启动，引擎报「创建事件循环失败」后 return，fn main 正常返回＝退出码 0；Linux 打包验收时把包解到别处、从错误 CWD 启动（缺 assets/mesh.spv），日志打出「渲染器初始化失败」紧接着「程序正常退出」，退出码还是 0 —— perf_run 只看到「游戏提前退出（code 0）」就当一次正常结束。
- **根因**：退出码 0 有两条通道都被致命错误借用了 —— fn main 正常返回，以及 event_loop.exit() 本身就是「正常退出」通道（run_app 返回 Ok），而「创建窗口失败」「渲染器初始化失败」两处致命分支用它收场，于是给 run_app 加的那道检查一条都抓不到。
- **教训**：致命路径必须 process::exit(1)，既不许说正常也不许退 0；源码扫描型判据要先去注释再扫（修 bug 时写的注释里就引用了「程序正常退出」，不去注释判据会自行满足），且第一版把扫描写成 code[i..].contains(...) 扫锚点之后的全部内容 ⇒ 第二处修复喂饱了第一处的断言，把事件循环那条改回 return 也照样绿 —— 判据必须把源码在锚点处切成两半、各自只在自己那一半里找。
- **来源模块**：平台与杂项

## 判38. 配置字段「存在且有人读」不等于接线完成，roundtrip 测试对默认值毫无分辨力

## 判39. 状态机把失败写进 done，闸门于是永远显示 DONE —— 不信 DONE、cat 状态文件才发现里面是 pass:false

- **症状**：跑闸门 status 得到 noise/smoke/patrol/vvl 全 DONE，看似清账；没有相信这个 DONE，把状态文件 cat 出来，里面赫然是 "patrol": {"ok": 0, "pass": false, "bad": [12 条 FAIL]} —— 那条 FAIL 是显存被外部负载占着时跑的失败尝试。
- **根因**：run_step() 无论成败都写进 done，而 main() 用 s not in done 决定下一步、status 又只看键存不存在 ⇒ 一次失败尝试被永久冻结成「已完成」，之后每次运行都跳过它，状态显示得整整齐齐却是假的。
- **教训**：审自己的工具时要把它的「输出」与它的「底层记录」对一次账（本次是 status vs gates_state.json），两者一旦不一致，显示得再整齐也是假的；修法只能「只有通过才写 done，失败写进单独的 failed 下次重试」，并让 status 即使键在 done 里、只要记录写着 pass=false 就显示 FAIL。
- **来源模块**：平台与杂项

## 判41. ab_pair 不看退出码、aa_probe 代码与文件头不符 —— n≥5 的批次被悄悄降级成有效证据

- **症状**：批次不全（某些臂根本没跑成）时 ab_pair 照样给出臂间结论；aa_probe 文件头写着「有一次没解析出来就退 1」，实际 6 次里坏 4 次还打一行「噪声底」并退 0。
- **根因**：ab_pair 完全不看 perf_run 的退出码，只找不找得到那行 fps ⇒ 非 0 结果也被判为可用臂，教训 45 要求的「每臂 ≥5 对」就是在这里被悄悄违反的；aa_probe 则是代码与文件头各说各话（只在不足 2 次时才退 1）。
- **教训**：驱动器要看退出码并把「完成/请求/跳过」统计出来，批次不全一律退 2；臂顺序逐对轮转（奇数对 A→B、偶数对 B→A，ABBA）抵消「一对里第一次跑系统性偏快/偏慢」；自检用桩注入 STUB_RC / STUB_FAIL_EVERY 复现「每第 4 次失败 ⇒ 跳过 2 对退 2」，并留一条负对照（桩抖动在臂间对消、中位差 0.00、符号 2/4）证明尺子不会凭空造出效应。

## 判42. 交叉验证命令从来没跑起来过（目标没装），非 Windows 那条路漂到 2 错 12 警

- **症状**：铁律 E 写着「交叉验证 cargo check --target aarch64-unknown-linux-gnu」，而本机 rustup target list --installed 只有 x86_64-pc-windows-msvc —— 那条命令从来跑不起来（连依赖都编译不过），于是非 Windows 那条路一路漂到 2 个编译错误 + 12 条警告都没人知道。
- **根因**：不是代码错，是「判据的前置条件没人装」；这是当天第 6 处「判据没真跑过」的同形缺陷（前五处：survive 读空文件 / ab_pair 空串参数被吞 / .ps1 中文行尾吃掉下一行 / preview_glb 写到 C:\ / cap_safe 打印 SAVED）。
- **教训**：装上目标后暴露的真问题照修（cjk_glyphs 被 #[cfg(windows)] 门控而 font_cjk 无条件 use 它的表、vld3q_f32 要 *const f32、非 Windows 未使用导入），12 条 dead_code 用一行平台作用域的 cfg_attr(not(windows), allow(dead_code)) 收口时必须写明这不是给未接线代码开后门；验收两条都要绿 —— 交叉 check 0 error/0 warning，且 Windows 侧 build/test 仍 0 警告（dead-code 判据一个字都没松）。
