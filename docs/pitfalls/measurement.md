# 测量与统计 —— 误区与陷阱（14 条）

> 帧率口径、噪声底、A/B 设计、把噪声当效应
>
> 返回 [`docs/pitfalls.md`](../pitfalls.md)（总索引与全局综述）。
> 每条格式：**症状 → 根因 → 教训 → 类别**。根因里保留了「当时以为是什么」——那是最值钱的部分。

## 测1. AI 在自家门口绕圈、验收脚本在空仓里干响：波次清不掉与"交战 150 次 0 杀"都不是"AI 不努力"

- **症状**：survive 波次永远清不掉；测试报告"wave 3 集群 150 次交战、0 杀"；换弹期间 2.3s 窗口全是干响。（761db34, 2026-09-22）
- **根因**：① `Patrol/Idle` 航点是绕 home 画圆 `r=20+id*3`，而 wave 1 敌人生成在 83–91m 环上、视距 60m、`aidiag` 首次实证 `occluded=false` ⇒ 它们永远绕自家转圈、两军永远走不到一起（修法：圆心向目标推进 70%、半径封顶 18m，进视距后 Chase/Attack 自然接管）。② 瞄准容差 1.5° 在 60m 处 ≈1.6m 漂移 > 命中盒 ⇒ 打了不等于打中。③ `try_fire` 空仓时自动挂换弹，但**那一发丢失**，脚本整个窗口都在干响。
- **教训**：判"打中了没有"用 `weapons: shot #` 核对**实发**，不要用击杀数/交战数（同形：计分对任何敌方死亡都加分，有 NPC 自伤的模式里 `killed>=1` 不是命中证据；判 AI 自杀要看投弹与击杀是否同秒）；"它到底要去哪"必须能打印出来（`Npc::last_goal` 此前在日志里完全隐形，包抄目标点跳变那个 bug 就是这么藏了两轮）；行为类的"没效果"先证明它有没有真的走到/打到，再谈策略。
- **来源模块**：渲染管线

## 测2. 旧回放帧 + 低分辨率是双重不可靠：把圆柱底缘读成"悬空月牙"

- **症状**：据一张归档旧帧断言某构件是"悬空月牙"，放大到全分辨率后其实是 **∪ 形**——从上方看近侧底圈的正确轮廓；而"俯视该是 ∩"这个前提本身就是错的。
- **根因**：取证材料有两个独立的不可靠来源——旧回放帧（几何/机位已不是当前版本）与低分辨率（轮廓被读成另一形状），**两者叠加时最危险**。
- **教训**：立案前先看全分辨率原图，并优先用当前版本的新帧；对"这个形状应该长成什么样"这类前提要先花一次运行标定（同铁律 C 里"任何角度参数先拿已知物体标定一次朝向"），别把直觉当判据。
- **来源模块**：城市与几何

## 测3. raw 位移的单位是设备原始计数，而阈值按"屏幕像素"写 ⇒ 真实移动被全部丢掉

- **症状**：捕获状态下视角完全转不动，而鼠标确实在动、事件也在收。
- **根因**：WSLg/Xwayland 下 XInput2 raw 位移的单位是**设备原始计数（约为屏幕像素的 4 倍）**，旧代码却用 `MAX_LOOK_DELTA_PX = 512` 这个像素量纲的绝对阈值做守卫 ⇒ 正常单次移动被当成传送/跳变整条丢弃。
- **教训**：阈值/守卫必须标出**量纲与来源**（device counts vs px），并写明它属于哪条路径；修法是 raw 增量直接驱动视角；**一个会丢输入的守卫必须带上丢弃计数**，否则只能靠"完全转不动"这种终态被人发现。
- **来源模块**：输入与交互

## 测4. 注入 harness 把瞄点定在离地 0.8m ⇒ 每发都打在腿/臂倍率区，"打不动"被误读成掩体问题

- **症状**：真机残局 3 只 NPC 站定在环外 12.8m，harness 打印 `giving up on npc#16 after 6 tries (stale stand line or behind cover)`，kills/shots = 11/150（约 13 发/杀）—— **当时以为**是"NPC 在掩体后打不到"。
- **根因**：`target_angles` 的瞄点是 `ny + 0.8`，按引擎部位倍率（头 1.5 / 胸 1.0 / 臂 0.8 / 腿 0.6）正好落在腿/臂区 ⇒ 每发只有 0.6–0.8 倍伤害；wave 2 的 NPC 是 120HP，按 0.6 倍算恰好约 11 发/杀，与实测吻合 —— 是 harness 缺陷，不是引擎缺陷。
- **教训**：**先证明"打中了该打的地方"再解释打不死**：命中/伤害统计必须打印实际命中部位与倍率；瞄点抬到 `ny + 1.25`（胸腔 = 1.0 倍）并让 smoke / survive 共用同一套换算；"工具自己不好用"要单独记账，别让它伪装成引擎缺陷。
- **来源模块**：输入与交互

## 测5. 滚轮切枪根本没进日志：0 不是"没生效"，是尺子量不到

- **症状**：新探针在验证层下按完 1..9 再滚两格，摘要报 `switches after 9 digit keys: 8` 与 `switches caused by the two wheel notches: 0 (0 = the wheel path did not fire)`，看上去就是 `PostMessage(WM_MOUSEWHEEL)` 到不了 winit，当时差点写成"现象不存在"。
- **根因**：滚轮那条路（`main.rs` 的 `MouseWheel` → `Game::cycle_weapon`）直接调 `WeaponRack::switch_next/prev`，**绕过了 `Game::switch_weapon` 里唯一那行 `weapons: 切枪` 日志** ⇒ 日志里永远不会有滚轮切枪；0 不是"没生效"，是量具量不到。
- **教训**：任何"计数为 0"的结论先问"我的量具量得到这件事吗"——抽出共用的 `log_switch_if_changed(prev, tag)`（标签 `切枪` / `滚轮切枪`），且探针必须自带"注入没生效"告警（数字键 < 7 次就 `!!`），否则"探针没驱动到"会被静默记成通过；读被重定向的日志要 `FileShare.ReadWrite`（否则撞 being used by another process），一次 F12 会打两条同路径日志 ⇒ 数**去重**值才是文件数。
- **来源模块**：游戏逻辑

## 测6. 阵亡计数漏掉主路径：军情自报 35，实际 68

- **症状**：170 秒 128v127 会战里 `command:` 行红营自报阵亡 35，而三个连强度合计 60 ⇒ 实际 128−60 = 68（蓝营 79 vs 123）——司令看到的伤亡只有真相的一半。
- **根因**：阵亡有两条路，计数只挂在其中一条：`damage_npc`（子弹/爆炸主路径）当场 `npcs.remove()`，而 `round_kills_*` 只在 `update_stress_respawns` 里扫"还留在数组里的 `hp<=0`" ⇒ 主路径一个都没计。
- **教训**："扫描容器找残留"式的兜底统计**天生漏掉"当场删除"的主路径**——同一事件的所有写入口必须收成一个 `tally_round_deaths(team, count)`；红测 `every_death_path_is_counted_in_the_round_tally`（修前 left 0 / right 1）要分别走两条路再断言总数。
- **来源模块**：游戏逻辑

## 测7. 军情连强度把同帧尸体算成活人：66 行里 6 行 `击杀 + Σ强度` 超出编制

- **症状**：真机会战日志 66 个阵营行里有 6 行「击杀 + Σ强度」比编制多 1~3 人——**是把这条不变式做成可重跑工具逐行检查才发现的**；去掉修复后实测 left 64 / right 63。
- **根因**：军情汇总按「在 npcs 里」计数 ⇒ 本帧刚阵亡、还没被清场的尸体**同帧既算活人又算阵亡**；而 `update_ai` 里的军情汇总排在 `update_stress_respawns` 之前，这个窗口每帧都存在。
- **教训**：口径写"活着的人"就按 `hp > 0.0` 判，别拿"在容器里"当代替品；不变式要做成可重跑工具（`tools/battle_tally_check.py`），退出码按"三种结局"约定：**0 = 扫过且干净 / 1 = 有命中 / 2 = 根本没跑成**；⚠️ 写这个工具时把 杀(U+6740) 打成了 伤(U+4F24) ⇒ 一行都匹配不上，而它老老实实报了「did not run」而不是「OK」——这正是那条约定要挡住的假通过。
- **来源模块**：联网与命令

## 测8. 军情快照不同源：击杀是本帧的、强度是上一 tick 的，两个数天生对不齐

- **症状**：修掉"尸体被算成活人"之后，日志里**仍有 9/66 行**超出编制 1~3 人 ⇒ 说明还有第二个原因（修完第一因别收工）。
- **根因**：`kills` 在 tick 判定**之前**赋值（每帧都新），而连报告要等 0.5s 的节拍 ⇒ 日志行里「击杀」是这一帧的、强度是**上一 tick 的快照**；**当时以为是计数又错了，其实是快照不同源**——临时埋点实测：33 974 帧里 `k + alive + corpse == 编制` 100% 成立，而 `rep != alive` 出现在 4 012 帧，差值恰好是"这一 tick 刚死的人"。
- **教训**：同一条不变式里的两个量必须来自**同一次刷新**（`self.kills = kills` 移进 tick 之后）；用埋点把"计数错"与"快照不同源"这两类原因分开（验完即删）；验收用真机长跑（150 秒会战 60/60 行满足不变式、工具 exit 0），而不是"改完看着对了"。
- **来源模块**：联网与命令

## 测9. AB/成本地图驱动器静默降级：空串参数被吞、不看退出码、批次不全照收

- **症状**：`powershell -File perf_run.ps1 -Extra ""` 报 `Missing an argument for parameter 'Extra'`（空串在参数绑定里等于"没给实参"）⇒ perf_run 一个字都不打、`Run-Arm` 每次返回 null、每一对都判 incomplete，第一版成本地图就这样整批空转；更糟的是**失败诊断被我按模式过滤掉了**，文件里只剩臂标题，十几分钟后才知道参数压根没传进去。
- **根因**：驱动器把"我能跑出数"与"这次跑成了"混为一谈——被驱动者的退出码、实际完成的配对数、驱动器自己的输出过滤，三者都没进判据。同类：`ab_pair` 原先**完全不看 perf_run 的退出码**（只找有没有那行 fps），降级的批次被当成有效证据（教训 45 的"n≥5 对"就是这么被悄悄违反的）；`aa_probe` 文件头写着"有一次没解析出来就退 1"，代码却只在不足 2 次时退 1 ⇒ 6 次里坏 4 次照样打一行"噪声底"并退 0。
- **教训**：驱动器要读被驱动者的退出码、打印「完成/请求/跳过」并在不全时 **exit 2**（0=全可用 / 1=没数据 / 2=部分可用或没跑成）；诊断信息全量落盘，别按模式过滤；文件头写的判据必须与代码逐条一致，并用桩脚本注入退出码自检（"每第 4 次失败"⇒ 跳过 2 对退 2；全成功 ⇒ 4/4、顺序 AB BA AB BA、退 0，且桩抖动在臂间对消给负对照）。
- **来源模块**：工具与闸门

## 测10. 帧率口径：fps 是**某一帧**的 1/dt，同一行的 frame_us 却是另一帧

- **症状**：同一天先用 perf_run 量到"半速阴影 +58%（中位 101.8 → 161.2）"，随后用**完全相同**的默认配置跑四轮 A/A，均值却落在 131.3 / 130.6 / 137.9 / 146.8，中位 108.5 / 108.0 / 140.1 / 160.1 —— 同一二进制同一参数的散布比那个"结论"的臂间差还大；日志里长期存在"163.8 fps 配 7550µs（=132 fps）"这种自相矛盾的行。
- **根因**：旧 `PerfLog::frame(fps, ..)` 收的是调用方的 `last_fps = 1/上一帧 dt`（瞬时值），而同一行的 `frame_us` 是**本帧** render 耗时，两个不同帧的量被写进一行；半速阴影让帧时间在两种长度之间交替，1 Hz 采样落在哪一支全看运气 ⇒ 逐行中位数在 108~160 之间乱跳，单轮 A/B 可以随手指哪一边赢。
- **教训**：fps 必须是"**窗口内帧数 / 窗口时长**"并由日志模块自己算（纯函数 `window_fps`，除零返回 0 不产 NaN），补 `dt_us` 让 fps/frame_us/dt_us 三者同源可互校，列定义收口成 12 列的 `PERF_LOG_COLUMNS` 唯一真源（脚本按下标取的那几列要有测试钉住）；任何量化结论前先用 A/A 量噪声底，**小于底噪的差不算数**（噪声底不是常数，0.2~5.5%，每轮现场量）。
- **来源模块**：工具与闸门

## 测11. 审计基准线与引擎实际基准差 10cm ⇒ 所有接触缝的量级都是假的

- **症状**：`float_scan.py`（直读 GLB accessor min/max）报出"弹珠漂浮 / 整墙浮空"，读数看着很大（aud2 的结论就建立在这上面）。
- **根因**：预渲染脚本把**埋没规则线**（-0.05）当地面，而游戏里可见的地面是 +0.05 的平铺 quad ⇒ 一切接触缝被系统性放大 10cm：违规本身真实，但量级是毫米，属**假阳放大**。
- **教训**：审计基准必须与运行时真源对齐（拿 `renderer.rs` 的常量对照，别在工具里另写一份）；工具自纠后**被它判过的历史结论都要重估**（坡脚石/沙袋按错误基准过挖，砂袋底层 0.08→0.13 才找回被过挖的 5cm 设计墙高）；把"审计工具自纠"当元教训入册，并把判据留在工具里（全资产埋没扫描）。
- **来源模块**：工具与闸门

## 测12. 注入 harness 的"打不动"其实是瞄点落在腿/臂伤害倍率上

- **症状**：真机残局 3 只站定在环外 12.8m，harness 打印 `giving up on npc#16 after 6 tries (stale stand line or behind cover)`，`kills/shots = 11/150`（约 13 发/杀）——看起来完全像"NPC 缩在掩体后打不到"。
- **根因**：`target_angles` 的瞄点是 `ny + 0.8`（离地 0.8m），按引擎部位倍率（头 1.5 / 胸 1.0 / 臂 0.8 / 腿 0.6）正好落在腿/臂区 ⇒ 每发只有 0.6~0.8 倍伤害；wave 2 的 NPC 是 120HP，按 0.6 倍算正好约 **11 发/杀**，与实测吻合。是 harness 缺陷，不是引擎缺陷。
- **教训**：工具打印的失败理由（"behind cover / stale stand line"）只是它自己的猜测，不能当结论；先用一次手算校核（血量 × 部位倍率 vs 实测发数）再决定改哪一侧；修法 = 瞄点抬到胸腔 `ny + 1.25`（1.0 倍），且**不追爆头**（头区只有几厘米厚，移动靶上打不中是净损失）；"工具打不动/跑不起来"本身就是一条要单独记账的缺陷（教训 36），否则它会一直伪装成引擎 bug。
- **来源模块**：工具与闸门

## 测13. fps 列取的是某一帧的 1/dt，与同行 frame_us 自相矛盾，据此报出过错误的 +58%

- **症状**：先用 perf_run 量到「半速阴影 +58%（中位 101.8 -> 161.2）」，随后四轮完全相同的默认配置跑 A/A，均值却落在 131.3/130.6/137.9/146.8、中位 108.5/108.0/140.1/160.1 —— 同一二进制同一参数的散布比那条「结论」的臂间差还大；日志里长期存在「163.8 fps 配 7550µs」（=132 fps）这种自相矛盾的行。

- **来源模块**：平台与杂项

## 测14. 亲手写的 A/B harness 前提是错的：PT 的 SPIR-V 编进二进制，换磁盘 .spv 根本没有换被测对象

- **症状**：v1 harness 号称「同一 exe、只换磁盘 .spv、曝光用环境变量覆盖」，三次采集的结果 B/A 等于 1.0 报假 FAIL、或在噪声内报假 PASS —— 两种都是垃圾结论。
- **根因**：build.rs 在构建期读 assets/rt/pt_panorama.spv 并生成 pub const PT_FRAME_SPV: &[u32] = &[...] ⇒ PT 的 SPIR-V 是编进二进制的，换磁盘文件对 exe 毫无影响，三次采集测的是同一个着色器（作废的 harness 改成拒绝运行的存根留着记这个坑）。
- **教训**：验「同机位 / 同二进制 / 逐字」之前，先确认被测对象真的换了 —— 新 harness 改成先预编译 exe_old/exe_new（纯 CPU、不需要显存窗口），窗口内只复制 exe 文件，曝光仍走运行时环境变量覆盖。
- **来源模块**：平台与杂项
