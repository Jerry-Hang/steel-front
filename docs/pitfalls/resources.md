> 容量、越界、内存、线程、只增不减的缓冲
>
> 返回 [`docs/pitfalls.md`](../pitfalls.md)（总索引与全局综述）。
> 每条格式：**症状 → 根因 → 教训 → 类别**。根因里保留了「当时以为是什么」——那是最值钱的部分。

## 资1. "先建新的再拆旧的"：换一把更小的枪也会重建在飞缓冲，按一下 2 就整台设备消失

- **症状**：切枪（AK-12M 63283 顶点 → AK-104 11705 顶点）时日志刷 2576 行 `device lost`，表现是"切枪 = 整台设备消失"；分配失败时切枪瞬间 panic，或留下非 null 的已销毁句柄（阴影 pass 会把它绑上、退出时二次 destroy）。（b8ae502, 2026-09-15；921097c, 2026-09-23；131ecc4 & 1afb7fc, 2026-09-24~26）
- **根因**：旧判据 `need != capacity` 在**换成更小的枪**时也重建缓冲 ⇒ destroy 正在被 GPU 使用的 buffer；注释从 2026-08-18 起就写着"切枪永不重建"，但判据写成了 `!=`，与注释不符（同形态：`set_props` 先 unmap/destroy/free 旧三件套再 create，create 失败就留下已销毁却非 null 的句柄）。更隐蔽的一处是内存映射失败：`unmap` 已经执行，`.expect()` 之外的任何"优雅返回"都会把 `gun_mapped` 留在指向未映射内存的悬空指针上，下一枪就是野地址写；`set_soldier_mesh` 里 `if let Ok(..)` 吞掉索引映射失败，却照常把 `soldier_index_count` 设成 `indices.len()` ⇒ draw call 按这个数读未初始化显存。
- **教训**：生长判据一律 `need > capacity`（不是 `!=`），真扩容前 `device_wait_idle()`；任何"替换在飞资源"按"先建新的 → 映射成功 → 才毁旧的 → 再换句柄"排序，失败只 log + 降级（这一枪/这张图的道具不画，其余照跑）并保留旧句柄，`destroy` 之后立刻置 null；失败路径要让计数与句柄同源（扩容失败必须把 `gun_*_count` 恢复成旧值，否则"旧缓冲 + 新计数"= 越界抓取；重映射失败则指针置空、由入口判据让下一枪走重建分支）；`.expect()` 不许出现在 Vulkan 调用后 8 行内，`if let Ok` 不许吞 Vulkan 结果，两条守卫都要先跑成红的。
- **来源模块**：渲染管线

## 资2. 修好视觉缺陷却把帧率从前 82 推过拐点：阴影 pass 全量画道具实例 ×4 级联

- **症状**：给围合排楼补分段（+56 栋）后，同机位 fps **82→47**，而 `RV3D_NO_SHADOW` 对照回到 106 ⇒ 代价全在阴影 pass：全量画道具实例 ×4 级联被推过了拐点（renderer 里早有注释标注这是已知浪费）。
- **根因**：道具实例在阴影 pass 里没有 LOD，视觉修复带来的实例增量直接乘到 4 级联阴影上；当时"视觉缺陷修复优先、阴影级联剔除列为下一专项"是有意识的取舍，但代价没有当场归因到 pass。
- **教训**：补视觉缺陷时必须同时量同机位帧率与 NO_SHADOW 对照，把代价归因到具体 pass 再决定是否当场修；修法是阴影专用几何烘成 AABB 盒壳 LOD（872k→482k 三角、fps 47→80，LOD-off 对照 62），且**任何失败自动退回全量**（退化方向 = 多画三角形，永不缺阴影）；验收看"帧差强变化只落在阴影边界"（4.48% 像素）。
- **来源模块**：城市与几何

## 资3. 静音时声部永不退队：队列无界增长，解除静音后旧枪声齐鸣

- **症状**：音量 0 之后每一发枪/每一次命中都堆一个永不退出的声部（每秒十几发，静音一小时就是几万个），每帧还要遍历一遍；**解除静音时累积的枪声一起响**。
- **根因**：`Mixer::mix` 对 `gain <= 0.0` 的声部直接 `continue` ⇒ 游标**永不前进**、声部**永不 finished**——"跳过播放"这一步恰是它退场的唯一机会。
- **教训**：凡是"跳过某个对象的处理"的分支，必须回答"它还会不会自己结束/推进"（听不见 ≠ 时间停止：静音分支仍要推进游标，非循环到点判 finished、循环取模回区间，`total = 0` 不做取模除零）；红测 `mixer_retires_voices_even_when_muted`（静音下播 20 个短 clip，几帧后必须 0 个活跃声部）+ `unmuting_does_not_replay_stale_voices`。
- **来源模块**：游戏逻辑

## 资4. 同一份数据报里两条路径两种待遇：裸 `with_capacity(报文里的 u16)` 让 2 字节放大成 1.6MB

- **症状**：没有任何现场症状，是逐条核防御时发现的：同一份数据报的 Snapshot 分支是裸的 `Vec::with_capacity(n)`，而 `n` 是**报文里的 2 字节 u16**（最大 65535）⇒ 伪造报文只花 2 字节就能让接收方一次预留约 1.6MB（NpcSnapshot 约 28B × 65535），放大比约 8e5:1。
- **根因**：**当时以为"容量提示"和"接受多少条"是一回事，其实只需压容量提示**——旁边 ObjectiveState 分支**早就**这么防了（`n.min(MAX_OBJECTIVE_POINTS)`，注释写着「防止攻击者仅凭 2 字节 count 触发大分配」），两条路径写在同一个解码函数里、待遇却不同；逐条读取本来就有 Reader 边界检查，所以语义不用改。
- **教训**：凡"报文里的计数直接当容量提示"，一律先封顶到协议上限；**同一个解码入口里成对的路径要一起审**——发现一条防了、另一条没防，本身就是缺陷；判据三条：capacity hint 封顶（红证：去掉 `min` ⇒ 立刻红 65535/1024）、伪造 count=65535 得 Truncated 不 panic、快照路径任意前缀均为 Truncated。
- **来源模块**：联网与命令

## 资5. 同机跑 llama-server 的 GPU 推理把设备打掉：改 CPU 推理（-ngl 0）+ LLM 模式限帧 90

- **症状**：运行 LLM 模式时出现 GPU device lost、卡死。
- **根因**：语料本条正文为空，仅标题给出处置 —— llama-server 默认走 GPU 推理，与游戏进程争抢同一块 GPU；改为 CPU 推理（-ngl 0）并给 LLM 模式加 90fps 帧上限后不再设备丢失（更细的机制语料未说明）。
- **教训**：把外部推理进程与渲染器放同一台机器上跑时，先假设它们会抢设备/显存 —— 推理侧固定 CPU（或显式限制显存），被测模式加帧上限，并把外部负载写成准入判据（同仓后续实测确实反复被外部占用挡在 cap_safe 的显存准入门之外，且正确做法是拒绝启动而不是放宽门槛）。
- **来源模块**：平台与杂项
