# 工具与环境 —— 误区与陷阱（14 条）

> shell、编码、构建、缓存、脚本自身的坑
>
> 返回 [`docs/pitfalls.md`](../pitfalls.md)（总索引与全局综述）。
> 每条格式：**症状 → 根因 → 教训 → 类别**。根因里保留了「当时以为是什么」——那是最值钱的部分。

## 工1. 构建与工具链的两个静默假设：release 里 `debug_assert` 不存在、0.18 秒的 `Finished` 不代表 spv 已同步

- **症状**：① 64 核/128 线程以上的机器一启动就崩（`near_prefix[w]` index out of bounds），本机复现不了；② 为拍"改前"帧做 checkout→重建→还原→重建，最后一次只用 0.18s（缓存命中），误当已同步 ⇒ 随后的 VVL 轮、冒烟、巡逻**全跑在过期 spv 上，三道门作废**，抓出来只靠一条哈希比对（`5d0d2117…` → `49baeef0…`）。（c603ef5, 2026-09-25；a94496f, 2026-10-01）
- **根因**：① `cull_and_upload` 的段数是裸的 `pool.workers()+1`，两张前缀和表是栈上定长 `[u32; 64]`，只靠 `debug_assert!(nw <= 64)` 兜着——而本仓 `[profile.release]` 用默认值（debug-assertions=false），release 里那句断言根本不存在。② PT 的 SPIR-V 是**编译期内嵌**，而 `assets/*.spv` 是**运行时从磁盘读**；cargo 以 build.rs 指纹决定是否重跑，内容回到旧状态时可能判定无需重跑，于是 `Finished` 照打、磁盘 spv 却没回写，"改→回退→还原"三步之后两者各停在不同版本。
- **教训**：兜住越界只能用硬夹/`clamp` + 常量（`CULL_MAX_SEGMENTS=64`；段数只影响并行度、不影响结果，所以夹住零行为变化），不要把 `debug_assert` 当安全网；改过着色器源码后判据是 **spv 哈希**而不是"我编译过了"（碰过 `build.rs` 一律 `touch` 强制重跑，别信 0.x 秒的 Finished）；反向也成立——spv 哈希没变就说明改动没编进去（本次 `mesh.spv` `28788 B → 27404 B`、方向与量级都对）。
- **来源模块**：渲染管线

## 工2. 骑楼棚离墙悬空 0.35m（纯坐标算术即可判定），而用来取证的调试机位会谎报 FPS

- **症状**：44.0×2.6×0.35 的薄板"飘在墙外"——三排楼外墙面在 `cz+4.75`、棚内沿却在 `cz+5.1`；44m 长只有 0.35m 厚，平着色下顶底各一块均匀色、边缘无收头，剪影就是纸。这条改动被明确标注"未视觉验证"。
- **根因**：离墙量是**纯坐标算术**就能判定的（两个常量相减），不依赖看图；而当时能把机位对准 shop_block 的 `RV3D_CAM` 会**谎报 HUD 大号 FPS**：`cam_override` 分支提前 `return`，跳过了喂 `hud.fps` 的那行（同一二进制无 `RV3D_CAM` 显示 153，带它显示 0，而日志实测 146-152、`fps=0` 出现 0 次），于是"游戏卡死"的假象把取证搅乱；前景还有一坨来源未查明的白色薄壁交叉结构挡着。
- **教训**：能用常量算术判定的缺陷不要留给"看图"（先判离墙量、厚度、收头）；HUD 上的 FPS 与渲染器自己的计数/日志不一致时，先怀疑 HUD 那条赋值路径而不是引擎；取证通路本身有缺陷时，先修通路再继续取证。
- **来源模块**：城市与几何

## 工3. 键码有两套命名空间（winit KeyCode 序号 vs Windows 虚拟键码 VK），混用表现为"发出去了但游戏零响应"

- **症状**：注入工具 `cap_safe.ps1` 的 `-Keys` **从未生效** —— 脚本不报错、游戏不报错，只是什么也没发生；引擎侧另一路症状是 WASD/R 全部错位。
- **根因**：同一个整数在两套语义下都合法：引擎认 winit 0.30 的 `KeyCode` 枚举序号，而 `PostMessage(WM_KEYDOWN)` 的 `wParam` 必须是 Windows VK；把 `KeyCode` 当 VK 发出去，游戏收到的是另一个键，于是"键没生效"却查不出错。事后同一轮还查出窗口句柄也取错了（`Process.MainWindowHandle` 拿到的不是接收输入的那个窗口）。
- **教训**：跨边界传键码时把"哪套编码"写进类型/函数名，别传裸整数；用一张参数化键位表把映射钉死，升级 winit 先跑它；工具类判据不能是"消息发出去了"，必须是"目标进程的状态真的变了"；真因常常不止一个，修完一处要重跑同一判据直到症状消失。
- **来源模块**：输入与交互

## 工4. PIL 的默认 anchor 会把汉字底部切掉 3~4 行

- **症状**：生成的字模底部被切掉，汉字看起来缺笔画/压扁（3~4 行像素），而生成过程没有任何报错。
- **根因**：PIL 默认 `anchor='la'`（左-ascender）按拉丁基线定位，而**汉字的 em 盒顶在 ascender 之上** ⇒ 字形整体被压低、底部出界被裁；必须显式 `anchor='lt'`。
- **教训**：用图像库默认参数生成字形/图集前，先做一次**单字标定**（渲染一个满幅汉字，检查四边留白），并把 anchor/基准写死在脚本里；这类缺陷在整表缩放与裁剪时不会报错，只能靠人眼或像素级标定发现。
- **来源模块**：输入与交互

## 工5. 调试相机下"看不到士兵"不是模型也不是取景，是剔除参考点还钉在玩家眼位

- **症状**：用 `RV3D_CAM` / `RV3D_NPC_CAM` 取证时，相机眼前的士兵被整片剔掉，画面里看不到人。
- **根因**：`npc_occluded` 是以"玩家眼位"为中心的剔除——正常玩法里玩家就是相机所以正确，但调试机位把相机移开时玩家仍在原点 ⇒ 相机眼前的人被判为"从玩家位置看不到" ⇒ 剔除。
- **教训**：剔除/可见性判据的参考点必须与当前相机一致（新增 `cull_eye_override`）；调试机位取证必须带 `RV3D_NO_NPC_CULL=1`；"看不到某物"先看实例计数（perf 的 `npc=` / HUD 的 `I/P/C/A`）再看图，别一上来怀疑模型或取景。
- **来源模块**：游戏逻辑

## 工6. PS 5.1 按 GBK 读无 BOM 的 .ps1：行尾中文把**下一行代码注释掉**

- **症状**：按字节级规则（行尾字节 ≥0x80）扫 `scripts\*.ps1`，命中 **5 个脚本**、各丢 1~4 行真代码：`compile_pt.ps1` 吃掉 `$ErrorActionPreference = 'Stop'`（glslang 失败不再中止）、`pt_power_ab.ps1` 吃掉 `function Run-Case(...)`（脚本整体不可用）、`release_input.ps1` 吃掉 `$alive = 0`、`run_gameplay_smoke.ps1` 吃掉四处（含启动游戏与跑冒烟本身）；改脚本时新加的中文行尾注释又让守门测试当场变红（当天第二次被它救）。
- **根因**：某行以中文/全角结尾时，最后一个字节落在 GBK 首字节区间，解码器把行尾本身当成它的第二个字节吃掉 ⇒ 下一行被并进这一行；若这行是注释，**下一行代码就被静默注释掉**——不报错、不看代码根本发现不了（同一机制还表现为 GBK 解出 `Unexpected token '}'`）。
- **教训**：`scripts/*.ps1` 行尾必须是 ASCII（中文写在行中间无害），判据 = 守门测试 `powershell_scripts_never_end_a_line_with_a_non_ascii_byte` 扫 `scripts\*.ps1` 并**在扫到的文件数 <10 时报路径错**（防"没测到"与"测到 0"混淆），更强的判据是 `Parser::ParseFile` 零错误（它按 ANSI 解码 BOM-less 文件，与运行时一致，顺带覆盖"字符串里的中文吃掉收尾引号"）；敏感性要当场验（临时放一个中文行尾的 .ps1 ⇒ 红且指名文件:行号）。
- **来源模块**：工具与闸门

## 工7. 注入脚本的键码空间搞错：winit `KeyCode` 当成 Windows VK 发，游戏一个键都收不到

- **症状**：截图脚本 `cap_safe.ps1` 的 `-Keys` **从未生效**（"发出去了但游戏零响应"），于是枪械姿态这类功能只能在引擎内验证，实机键位始终无法取证。
- **根因**：投递给 Windows 的键码空间用错了——脚本把 winit 0.30 的 `KeyCode` 枚举序号当成 **Windows 虚拟键码 VK** 塞进 `PostMessage`，两套编号体系并不相同（标题同时点出"窗口句柄"也取错了；正文未展开细节）。
- **教训**：注入脚本里只允许出现 VK 码，键码表单独维护并注明来源（winit 侧那张表由 `ui.rs::winit_keycode_indices_match_table` 锁死，升级 winit 先跑它）；端到端验证要选一个"按下去必定改变画面或日志"的键，别拿"脚本没报错"当生效证据——`pm_play.ps1` / `gameplay_smoke_pm.py` 才是实测有效的参照实现。
- **来源模块**：工具与闸门

## 工8. 仓库里的 .spv 与仓库里的 build.rs 不自洽：一次"修复"制造了这个 bug

- **症状**：`assets/*.spv` 每次构建都变脏；第一次处置把 7 个被跟踪文件换成"另一次构建的字节"（体积 +7%），于是**从那以后每次 `cargo build` 都会把它们改回去**；另外 `cargo clippy --all-targets` 一次就能把 7 个 .spv 全部改脏（dev profile 的 naga 输出与 release 不同，`mesh.spv` 27572 → 29432 字节）。
- **根因**：上一版先写了「naga/rspirv 输出不是逐字节确定」这个**没测就下的判断**（实测强制重跑两次 MD5 完全相同，生成器确实是确定性的）；真因是仓库里提交的 .spv 过期/来自别的构建状态——逐 opcode 对比显示两版差别只是 `OpName`/`OpMemberName` 调试符号名，而 `build.rs` 两处 naga 调用都传 `debug_info = None` ⇒ **当前 build.rs 根本不可能生成带头名字的 .spv**。"同一份临时配置下重跑两次相同"之所以通过，是因为**跨配置的差异被漏掉了**。
- **教训**：仓库里的二进制必须与仓库里的生成脚本自洽（提交真正产出的那一份，并做逐文件尺寸/哈希核对）；"我改了它就好了"要先证明是修复而不是制造（对照组也要跑）；确定性验证要跨配置比、还要与 HEAD 比；dev/clippy 构建下文件已存在就不写，避免跑一次 lint 污染工作区；这 7 个是运行时从磁盘读的着色器，换字节后必须实机验证（地面细节层在、窗洞/烟囱在、树冠体积正常、枪口朝前）。
- **来源模块**：工具与闸门

## 工9. 引擎压根没起来，冒烟却报成功：TTY 会话没有图形环境变量

- **症状**：重启后从 TTY/自动化 shell 跑冒烟，引擎报「neither WAYLAND_DISPLAY nor WAYLAND_SOCKET nor DISPLAY is set」，而 KWin 其实还在跑、`/run/user/1000/wayland-0` 就在那里；调用方拿到的是一个说不清的失败（配合退出码修复才发现）。
- **根因**：本 shell 是 TTY 会话（`XDG_SESSION_TYPE=tty`），**不继承图形会话的环境变量** ⇒ 引擎起不来；而脚本侧没有把"引擎没起来"与"跑过但失败"分成两种结局。
- **教训**：缺环境变量时**能自动补就补**（socket 存在就用 `WAYLAND_DISPLAY=wayland-0` 继续，实测设备正常选中），补不上就 fail-closed 退 2 并明说"没跑成"，别让调用方拿到一个说不清的失败；"引擎没起来"必须有独立退出码。
- **来源模块**：工具与闸门

## 工10. 调试开关本身改变了被测量对象：Block 的纯绿触发 is_tree，把立方体改画成二十面体

- **症状**：RV3D_DEBUG_KIND 开出来的按种类着色图里，柱廊王冠出现「四尖星」；后来确认这类图无法区分「物件本来是星形」与「工具把立方体变成了星形」⇒ 那一半证据作废（不是翻案，是证据不合格）。
- **根因**：给 ObstacleKind::Block 的纯色是 [0,1,0]，且保留 tint.w = shape.tag()，正好同时命中 build.rs 的树冠兜底两条判据（is_foliage(t) = t.g > t.r && t.g > t.b*1.4，且 0.5 < shape_tag < 1.5）⇒ 开关一开，全城 Block 里所有 Shape::Legacy 立方体被改画成二十面体（Block 是最大一族，779/1789）；其余五色都判不中（红/蓝/品红 g>r 假、黄相等、青 g > b*1.4 假）。
- **教训**：调试可视化开关也是「仪器」，上色前先核它会不会被渲染侧的启发式判据吃掉（改橙色 [1.0,0.55,0.0] 让 g>r 永远为假，并把理由写进注释）；更大的隐患同源 —— 这条按颜色猜树冠的兜底在正常画面里也生效，任何 Shape::Legacy 方块只要 tint 绿得过头就会被画成树冠团块，正解是给手写 marker 的构造点显式打标签后删掉 is_tree 整行。
- **来源模块**：平台与杂项

## 工11. 游戏 stderr 随控制台消失，鼠标失效与卡死只能盲猜

- **症状**：游戏出现鼠标失效/卡死这类问题时，除了随窗口一起消失的控制台内容之外没有任何日志，排查只能靠猜。
- **根因**：启动器没有把游戏子进程的 stderr 重定向落盘 —— stderr 随控制台一起丢失（语料本条正文仅标题，未再展开）。
- **教训**：启动器必须把子进程 stderr 落到 logs/play_latest.log.err 这类固定路径；下游判据要读那份 stderr 文件（同仓另一处教训：引擎只写 stderr，判据读 stdout 的 .log 会读到空文件并当成通过）。
- **来源模块**：平台与杂项

## 工12. docs 里的一个 NUL 字节：read 工具直接报 binary file，终端里只显示空白

- **症状**：read 工具对 docs/HANDOFF-soldier.md 直接报「binary file」，而文件内容是合法 UTF-8；在终端里那一处只显示成空白，完全看不出异常。
- **根因**：文件里有 1 个 NUL（0x00），位置正好在一句「· 0 警告 ·」里 —— 那个 0 被写成了 0x00；发现方式是审计工具把扫描面扩到 docs/HANDOFF-*.md 时被 read 拒绝读取。
- **教训**：文本文件不许含 NUL，要用判据扫（覆盖 docs/*.md + src/**/*.rs + build.rs/build_spv_rt.rs，报错逐文件给行号与字节偏移），并自检「至少扫到 30 个文件」，否则路径写错也会静默通过；「工具读不了这个文件」本身就是一条要修的缺陷，不能当成已知限制绕过去。
- **来源模块**：平台与杂项

## 工13. 每帧路径上的「硬件不支持」告警刷屏，一次性闩自己写成恒真

- **症状**：RV3D_FORCE_SIMD 指向硬件不支持的档位时日志被同一条告警刷屏（一帧最多十几行）—— 三个调用点（地形 morph 每级一次、视锥剔除每段最多 9 次、冲击波每帧一次）都在每帧路径上，而这其实是一个恒定条件。
- **根因**：告警没有闩；改成共享的 OnceLock 一次性告警后，新写的测试第一次跑就红，抓出闩本身写错了 —— *get_or_init(|| true) 恒返回 true，闩的是「打过」而不是「本次打没打」。
- **教训**：恒定的坏消息报一次就够（与 set_hud_quads / warn_npc_cap_once / PT 盒上限同款：该报的报一次、不该刷屏的一次都不刷），且一次性闩必须由「第二次调用返回 false」的测试钉住；触发条件写清楚免得以为不可达（RV3D_DISABLE_AVX512=1 + RV3D_FORCE_SIMD=avx512，或 Intel 11/12 代上照文档强制 avx512）。
- **来源模块**：平台与杂项

## 工14. 检视模式白屏：共享的第一人称顶点变换没做模式区分，世界中心的枪被挪出长焦框外

- **症状**：RV3D_INSPECT=1 检视模式显示纯白空洞，什么都看不见。
- **根因**：静态顶点管线回归 —— fp_gun_pre 在检视模式也套用了第一人称矩阵（view_inv × anchor × ~0.25 scale），把世界中心 (0,1,0) 的枪推到相机旁 0.6m、偏轴 0.25m，正好落在 14.5° 长焦框外。
- **教训**：检视模式要用 Mat4::IDENTITY（顶点本来就是世界坐标、相机在轨道上），第一人称路径保持不变；共享的顶点/矩阵计算每加一个消费模式都要问「这条路径在这个模式下还成立吗」，改了必须双模式（第一人称 + RV3D_INSPECT）截图验收。
- **来源模块**：平台与杂项
