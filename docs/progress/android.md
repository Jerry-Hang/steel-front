## 1. 起点与诊断（`6b80f92`）

**用户提问（原话）**：「画面这么朴素为什么只有 23 帧？暗区突围开高画质 120FPS 都稳」

诊断链（同一次实测，`6b80f92`）：

| 诊断臂 | 读数 | 出处 |
|---|---|---|
| 阴影 map pass **每 2 帧重画** | **23.4 fps** | `6b80f92` 实测 |
| 阴影 map pass **完全关闭** | **23.7 fps** | 同上 |
| 关掉**片元阴影采样**（只留 map pass） | **42.6 ~ 45.4 fps**（起点为 23.4） | 同上 |

⇒ 两条推论（本轮全部工作的出发点）：

1. **重画阴影图几乎不花时间**（23.4 → 23.7）。
2. **17~18ms 的阴影成本全在「逐像素采样」上**（23.4 → 42.6~45.4）。

**成本算式（原实现，照录）**：

- **9 抽头 ×（静态图 + 动态图）= 18 次 `textureSample` + 18 次 `smoothstep`**
- **2400×1080 = 2.59M 像素** × 18 = **4660 万次**依赖纹理读取 / 帧
- 23 fps ⇒ **每秒 10.7 亿次**

⇒ 唯一值得动的杠杆是**采样数**（这个方向是 §2 的排除法得出的，不是先验判断）。

## 2. 🔴 被推翻的假设（最值钱的一条）

> 本仓最重视这一类记录：一个**看起来非常合理**的成本假设，被实测直接否定。

| 项 | 内容 |
|---|---|
| 假设 | 每像素 4 次 `sin`/`cos`（逐像素旋转抽头核的角度）是热点 |
| 尝试 | **干掉三角函数**：改用**整数 hash + 8 档离散角表** |
| 实测结果 | 🔴 **零收益** |
| 处置 | **已回退** |
| 价值 | **排除了 ALU 假设，把矛头指向采样数** ⇒ 直接决定了后面四刀的方向 |

**如果没有这一刀，「砍采样数」这个方向不会出现**：18 次采样 + 每像素 4 次超越函数，先验看两者都贵。
是这一次否证把成本定位到了采样上（§1 的 17~18ms 与之互证）。

归档时按现行源码复核：角度仍由三角函数给出（`build.rs` 的 `cos(pcf_ang)` / `sin(pcf_ang)`）⇒ 回退到位。见附录 B。

## 5. 饱和：帧成本扫描 —— 阴影采样这条路走到头

**饱和结论（第 4 刀的直接产物）**：**砍到 3 次采样后再砍无收益** ⇒ **阴影采样这条路走到头**。

于是改用**已有的运行期开关**做**帧成本扫描**（同机同会话，装机读 logcat `renderer::frame`）：

| 配置 | fps | 相对基线 | 开关 | 出处 |
|---|---|---|---|---|
| 基线（MSAA 4x） | **37.0** | — | — | 帧成本扫描 |
| **MSAA 关** | **44.7** | **+21%** | `RV3D_MSAA=0`（0/1 = 关） | 同上 |
| 程序化贴图关 | 37.1 | —（原始记录未给百分比） | `RV3D_PROC_TEX=0` | 同上 |
| 传统顶点管线 | 37.1 | —（原始记录未给百分比） | `RV3D_NO_MESH=1` | 同上 |
| **阴影采样关**（**天花板**） | **47.0** | —（天花板，非收益臂） | `RV3D_NO_SHADOW=1` | 同上 |

⇒ **MSAA 4x 现在比剩下的阴影 PCF 还贵**，**是下一刀**（详见 §8）。

⚠️ 本表不替未给百分比的两条折算：37.1 vs 基线 37.0 只是**读数**，本记录不宣称它构成收益。

## 6. 两个真 bug（与性能无关，独立修复）

> 当轮把这两条并称「两个真 bug」；严格分类：**6.1 是红线相关的清理**（不是行为缺陷），**6.2 是行为缺陷**。

### 6.1 `61a999c`：`src/lib.rs::env_str` 零引用单行别名 ⇒ 撞 0 警告红线

`syscfg::cfg` 落地后，`env_str` 只剩一个**零引用**的单行别名。本仓「**0 警告**（dead-code=0）」是硬红线
⇒ 直接删掉（清理类，不是行为缺陷）。判据只能用 `cargo build --release` 验（铁律 F：`cargo check` 会重放缓存诊断）。见附录 B。

### 6.2 `0e99b4a`：`sync_cursor` 每帧重试 **+ 每帧打日志**

| 项 | 内容 |
|---|---|
| 守卫 | `want && !cursor_captured` |
| 取值 | `cursor_captured = grabbed \|\| locked` |
| 缺陷 | **抓取失败时永远是 `false`** ⇒ 下一帧守卫又成立 ⇒ **每帧重试 + 每帧打日志** |
| 为什么手机上必然触发 | **Android 无光标** ⇒ `set_cursor_grab` 必然失败 |
| 实测代价 | **962 行日志里 737 行是它（77%）**，把真正的性能日志挤掉 |
| 修法 | **只在模式变化时打**（`cursor_grab_logged`） |
| 修后 | **0 行** |

🔴 **口径必须写清，别把这一刀修歪**：

- **重试本身是对的** —— 窗口**可能变得可抓**，失败后继续尝试是正确的行为；
- **每帧打日志才是错的** —— 该修的是日志节流，不是重试逻辑。

出处：`0e99b4a`；同一组数字在现行源码 `src/lib.rs` 的 `cursor_grab_logged` 字段注释里（见附录 B）。

## 7. 顺带记下的平台事实（本机探测）

| 类别 | 事实 | 出处 |
|---|---|---|
| 扩展总数 | Vulkan 扩展 **140 个** | 本机探测 |
| **无** | `VK_EXT_mesh_shader`（本仓主路径）、光追、`VK_KHR_cooperative_matrix` | 同上 |
| **有** | `VK_QCOM_image_processing`(+2) / `VK_QCOM_filter_cubic_weights` / `VK_KHR_fragment_shading_rate` | 同上 |
| 高通 **ANF**（AI 超分 + 帧生成） | 要求 **Snapdragon 8 Elite Gen 6+** ⇒ 本机（**6 Gen 4 / Adreno 810**）**跑不了** | 同上 |
| 高通 **SGSR** | **BSD-3 开源、纯 shader** ⇒ **可用** | 同上 |
| GLES 的 `GL_QCOM_frame_extrapolation` | **在 Vulkan 下用不了** | 同上 |
| 路线影响 | 本仓主路径 `VK_EXT_mesh_shader` **在手机上不存在** ⇒ 本机走的是「**冻结维护的传统管线**」（铁律 A 的兼容回退）；`RV3D_NO_MESH=1` 是它的 A/B 对照开关 | 铁律 A + `src/engine/renderer/device.rs:306` |

**Android 上这些开关怎么注入**：`RV3D_XXX` 在 Android 侧映射为系统属性 `debug.sf.xxx`
（`src/syscfg.rs:11-22`：`RV3D_` 前缀去掉、转小写），故扫描用的开关即
`setprop debug.sf.msaa 0` / `setprop debug.sf.proc_tex 0` / `setprop debug.sf.no_mesh 1` / `setprop debug.sf.no_shadow 1`
（`no_shadow` 一例见 `src/engine/lighting.rs:236-237` 的注释）。

⚠️ 本节只回答「**有没有**」，不含接入成本与画质代价的评估。
