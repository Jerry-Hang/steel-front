## 39. 🔴 新线索（**待验假设**，非结论）：小物件集体不投影，而代码说它们该投

**观察来源**：重放的俯视存档图 `screenshots/tc_b_b.png`（BEFORE，非当前状态）。
按本仓规矩**只用它提出问题**。

画面里（营地，世界坐标约 `(-142, ·, -32)`）：
- **建筑有影子**（营地中央那条沿 z 的暗带、右侧楼房屋顶的明暗渐变）；
- **没有影子的**：树冠（4–5m 高、半径 ~2m）、货车、4 组沙袋堆、3 件拒马、灯杆。

**代码已经排除的解释**（`record_shadow_pass`，`renderer.rs:11840-11945` 逐段读到）：
1. ❌"marker 不进阴影图" —— **不成立**：`:11892` 明确
   `draw_shadow_range(vertex_buffer, index_buffer, INDICES.len(), marker_near, MARKER_SLOT_BASE)`；
2. ❌"阴影图覆盖不到" —— 阴影光空间范围 ±400m（`ShadowConfig::new(..., 400.0, 1.0, 800.0)`），
   营地在 142m 处，**在范围内**；
3. ❌"分辨率太低吞掉了" —— 2048² / 800m ⇒ **0.39 m/texel**，
   树冠直径 ~4m ≈ **10 纹素**，沙袋 1.45m ≈ 4 纹素，都不该消失（只有灯杆 0.2m 是真会丢）。

**而且更不该消失**：阴影 pass 对 marker 一律用**立方体**几何
（`self.vertex_buffer` + `INDICES`），所以树冠在阴影图里是一个**方块**——
即便近似得很糙，也应当投出一块方形影子。

⇒ **剩下三个候选，按优先级**：
| # | 假设 | 怎么验（都需要 GPU） |
|---|---|---|
| A | **静态阴影节流把 marker 跳掉了**：`record_shadow_pass` 开头有 `skip_static`/`skip_terrain`，且存在 `static_shadow_pass_is_scheduled_every_n_frames` 与 `shadow_pass_is_scheduled_every_n_frames` 两条测试 ⇒ 若"静态那一遍"被跳过而"每 N 帧"的周期很长，相机一动就看不到新影子 | 同一机位连拍 30 帧，看影子是否**间歇出现**；或临时把周期设成每帧再拍 |
| B | **深度比较侧被翻转**（阴影 pass 剔 BACK 时把远面写进深度 ⇒ 自阴影被 bias 吃掉） | 阴影 pass 单独设 `CullModeFlags::NONE` 拍一张，看小物件影子是否出现 |
| C | **normal offset / bias 对薄物件过大**：`(1.25+0.9·slope)·texel` + 常量 0.12m，对 1.2m 高的沙袋可能整片被推开 | 把 bias 减半拍一张对照 |

🔴 **本轮不做**：三条判据都要开图，而 `cap_safe` 从 08:23 起连续 6 次拒绝启动
（`GPU-BUSY: 3253 → 7794 → 7779 → 7707 MiB > 3200 MiB`，占用来自浏览器）。
**没有放宽 `-MaxGpuMib`、没有绕过闸门。**
⇒ 显存一回落，**这条优先于 §37.2 的王冠案**：
王冠是"某个角度看着怪"，而"小物件集体不投影"是**整幅画面的立体感**，
且它同时命中用户点名的"光线追踪场景"与"观感"两条主线。

📌 记这条的另一个理由：它又一次说明**重放旧图不能当结论，但能当线索**——
今天从同一批图里先挖出了帐篷缺陷（已修 `5c8703b`），现在又挖出这条。

### 39.1 用代码先把 §39 的候选 A/B 判掉，并把**观察本身**降级为待复核

读 `record_shadow_pass` 的分组（`renderer.rs:11747`、`:11763`）：
```
// 静态组：地形 / 地面实例场 / marker / 道具；动态组：NPC 盒柱球 / 士兵 GLB
let skip_static = !draw_static;
```
⇒ **建筑也是 marker**（同一个 `MARKER_SLOT_BASE` 带、同一次 `draw_shadow_range`）。
而回放图里**建筑明确有影子**。所以：

- ❌ **候选 A（静态组被节流跳过）不成立** —— 它会把建筑一起跳掉，与观测矛盾；
- ❌ **候选 B（阴影 pass 绕序/bias 吃掉自阴影）大概率不成立** —— 同理会一并影响建筑；
- ⏳ 剩下唯一还站得住的是 **C：小物件的影子太短/太细，在 0.39 m/texel 下几乎不可分辨**。
  1.2m 高的沙袋堆、1.25m 的拒马，即便正对太阳方向也只有约 **3 纹素**长的影子。

🔴 **于是 §39 的"观察"本身要先复核**：我判"没有影子"用的是**相机上方 26m 的俯视图**，

⇒ **如果复核下来影子其实存在，§39 整条撤掉**，不留成"待查项"污染下轮的注意力。
（这正是 §23.15 护柱案的同型错误：**用超出仪器分辨率的观察去断言"没有"。**）

**复核判据（一次拍摄即可，不需要改代码）**：
在**眼高机位**（`fly:-142,1.7,-25:180,0`，距沙袋堆约 7m）拍一张，

## ❌ 圆柱网格也无罪 —— 并对我第 28 轮的判读做诚实修正（2026-09-12 第 30 轮）

```rust
pub fn cylinder(r: f32, height: f32, seg: u32) -> Mesh { frustum(r, r, height, seg, true) }
// frustum 内：pos = [c*rr, y, s*rr]   ← 轴向 Y，半径在 X/Z
//             caps at y = ±height*0.5 ← 总高 = height，原点居中
```

**轴向 Y、半径在 X/Z、总高 = height、居中 —— 与 `(半径, 高, 半径)` 的缩放约定完全一致。**
"圆柱网格轴向不符"的假设也不成立。

### 于是两条都排除了

- **矩阵侧**（第 29 轮）：17 段缩放/平移逐位正确，无退化轴，且已有测试守卫；
- **单位网格侧**（本轮）：盒与圆柱的约定都与矩阵的缩放语义一致。

### 🔴 对我自己判读的修正

第 28 轮我看到"杂乱红方块 + 细长尖刺"，推断为"退化缩放"。**两轮排查证明没有退化缩放。**
那么那幅图最可能的解释是：**那就是一个 1.79m 士兵在这个渲染器下的真实样子** ——
没有法线槽位（纯平着色）、无贴图、单一 tint、约 20–25m 距离。
方块状是"分段式人形 + 纯平着色"的必然结果；"尖刺"很可能是枪盒（0.07×0.10×0.62）
或薄几何在屏幕空间导数法线下的边缘伪影。

**⇒ 这恰恰就是用户说的"神人样子"本身。** 它不是 bug，是设计结果。

### 这改变了第④条的正确做法

**不该再继续查"为什么画错了"—— 它没画错。** 该做的是**让它在正确的距离上读得像个士兵**，
而这需要一张**大尺寸的士兵图**。可用的手段（按可靠性排序）：

1. **`RV3D_NPC_SCALE`**（未结案 7 提过）：把 NPC 放大 N 倍，等效于把 25m 拉成 7m；
2. **把相机放进人堆**：关剔除后有 255 人在场，`RV3D_NPC_CAM` 的目标换成
   "矩阵已验证在正确位置"的 v0 一类 NPC；
3. **放弃"近距离单兵"**，改为**在正常游玩视角下评估整体观感**（这才是玩家真正看到的）。

**建议下一轮先试 1 与 3**，因为"玩家在正常视角下看到的士兵是什么样"才是第④条真正要回答的问题。

# ✅ 未结案 #9 结案：mesh 着色器通过严格 `spirv-val`（2026-09-15）

## 症状与根因

- 症状：`spirv-val --target-env vulkan1.3 assets/mesh.spv` 非零退出 ——
  `[VUID-StandaloneSpirv-None-10684] the Workgroup storage class has a explicit layout from the Offset decoration`。
  **7 个被跟踪的 `assets/*.spv` 里只有它一个失败。**
- 根因（在 naga 里，不在我们的 WGSL 里）：**naga-30.0.0 `src/back/spv/writer.rs:3597`** 的
  `decorate_struct_member` **无条件**写 `Offset`，不看 storage class。而 `Offset` / `ArrayStride`
  在 SPIR-V ≤1.3 合法、**1.4 起对非 `Block` 类型禁止**，mesh（`MeshShadingEXT`）又**必须**用 1.4。
  `global_needs_wrapper` 与全部 `WriterFlags` 都查过，**没有任何开关可以关掉它**。

## 修法 `build.rs::strip_workgroup_explicit_layout(&mut Vec<u32>)`

- 由 `compile_wgsl_mesh` 调用：先**只从 storage class = Workgroup 的 `OpVariable`** 出发算类型可达闭包，
  再删掉目标类型落在闭包里的 `OpMemberDecorate … Offset` / `OpDecorate … ArrayStride`
  （连同 `MatrixStride` / `RowMajor` / `ColMajor`）；**构建期自检重扫输出，还有残留就 `panic!`**。
- 🔴 **带 `Block` 的类型（`_struct_300/303/308` = Uniform / StorageBuffer / PushConstant）一个字节都不许动** ——
  那是主机侧写入的缓冲布局，动了就是**静默错位**。
- **为什么它语义无损**：Workgroup 内存主机侧永不触碰，着色器只按 `OpAccessChain` 的成员索引访问、
  偏移由驱动自算 ⇒ **任何内部自洽的布局都等价**。

## 测量 / 回归 / A/B / 验收

- **7 个 `.spv` 现在全部 `spirv-val --target-env vulkan1.3` exit 0**（`mesh.spv` 在 `vulkan1.4`
  与默认 target 下也过）；`assets/mesh.spv` **27572 → 27300 B**（删掉 17 条装饰指令）。
- 两条测试（`src/engine/renderer.rs` 模块 `workgroup_layout_tests`）**锁住两个方向**：

  `block_types_keep_their_offsets`（`Block` 类型必须**保留**偏移）。**两条都验证过会真的红**：
  临时去掉 `strip_workgroup_explicit_layout` 的调用后，`spirv-val` 重新失败、第一条测试 **FAILED**。

### 22.1 `fix(render)` c9a625d：PT 帧相对游戏视角**水平拉伸 1.6 倍**

`pt_panorama.glsl` 两轴共用 `pc.a.z`，而该值是**垂直**半角正切
（`camera.fov` = `Mat4::perspective_rh` 的第一参数，`camera.rs:416` 实测）。
于是 PT 的水平半角被当成等于垂直半角，16:10 窗口下整帧相对游戏视角水平拉伸。

**判据（同一固定机位 `RV3D_CAM=fly:0,25,60:0,20`，三帧对照）**：

| 帧 | 远景门柱**跨径（中心距）**〔原标签误作「块宽」，实为 ~28m，见 §24.5〕 | 相对光栅 |
|---|---|---|
| 光栅参考 | 108 px | 1.00 |
| PT 修复前 | 180 px | **1.67** |
| PT 修复后 | 105 px | 0.97 |

比值 1.67 ≈ aspect 本身；地平线位置两帧一直一致（垂直本来就是对的）——
所以这个缺陷只在水平方向显形，**单看一帧永远发现不了**，必须同机位配对。

⚠️ **踩坑**：第一次改完 GLSL 后重采，两帧整幅 diff 只有 **0.01%**（等于没变）。
根因 = **PT SPIR-V 是 `build.rs` 编译期嵌入的**（`shaders::PT_FRAME_SPV`），
不是"运行时从磁盘读 `assets/*.spv`"那批主着色器 ⇒ 改 `.glsl` 后必须
`compile_pt.ps1` **再 `cargo build`**。判据 = 改完看 diff 百分比，不是看"我编译过了"。

### 22.2 `feat(render)` 746c466：PT 地面改采样光栅同一张程序化纹理

PT 地面盒原来是一颗均匀沥青反照率。单值反照率**表不出分区**：同机位分区表实测
道路区比光栅偏亮 **22%**，且地面反弹光（建筑基部 GI 的一阶项）整体偏暗。

改法：PT 描述符集加 binding 5（`COMBINED_IMAGE_SAMPLER`），两条 PT 管线

着色器对盒 0 按 `(xz+256)/512` 采样——与 `build.rs:785` 片元的 world-space UV 逐位一致。
`pt_refresh_dset` 不重写它（常驻资源不随场景重建换）。

复测：广场米色/道路深灰/中央黄虚线在 PT 帧全部出现；树冠分区 1.06→1.14
（地面反弹变亮，物理正确的方向）。剩余道路区差值来自光栅独有的地面细节层
（binding 9），属已知二阶差异，**不追**。

闸门：验证层整轮 **VUID=0 / ERROR=0 / WARN=0**（改描述符必开验证层，铁律 B）、
644 测试全绿、冒烟 ALL-OK（fps 186.3）。

### 22.4b 🔴 本节最有价值的产出：皮肤缺陷的**真实根因**是"砖块尺寸物体相对"

上面把它记成"皮肤不分材质类型"（审美缺口）。复核生成器后**升级判断**：
真正错的是**尺度**，而且这是代码可证的，不是口味问题。

* `procedural.rs::marker_skin`：`let rows = 4.0; let fu = (u*4.0 + off).fract();`
  ⇒ 皮肤在 **UV 0..1 内画 4 行 × 4 列**砌块。
* 铁律 B：**marker 用模板自带 uv（立方体 0..1，逐面）**。
* 两条相乘 ⇒ **砖块尺寸 = 面尺寸 ÷ 4，随物体大小线性缩放**：
  0.45m 护柱 → 11cm 砖；1m 花坛墙 → 25cm 砖；3m 围墙 → **75cm 砖**。
  实机图3 直接可见：花坛墙的砖明显比护柱的大一截。
  真实混凝土砌块是恒定 ~20cm，与墙多大无关。

**⇒ 这条比"石材穿木皮"严重**：它让**所有** marker 的砖块尺度失去物理意义，
而且物体越大错得越离谱。

**修复配方（已想清，未执行——它会改全城所有 marker 外观，必须配完整 A/B 与闸门）**：
1. 皮肤改按**世界空间平面投影**采样，与 `weather_stain` / `window_dark` / 地面纹理
   同一套做法（按 `abs(fnrm)` 主轴选投影平面，竖直墙用 `world_pos.xz`、水平面用 `xy`/`zy`）；
2. 缩放取"一个皮肤 tile = 4 砖 × 4 砖"，砖取标准 0.20m 高 × 0.40m 宽
   ⇒ `v` 方向每 **0.8m** 一个 tile、`u` 方向每 **1.6m** 一个 tile；
   分母必须与 `marker_skin` 里的 `rows=4` / `u*4.0` 对齐，**别在着色器里另猜一份**；
3. 采样器已是 REPEAT ⇒ 直接平铺；按 `dmax`（米/像素）做 mip 收敛，
   否则远距会重新引入走样（同 §树冠杂色那次教训：**收敛量必须用屏幕足迹，不能用视距**）；
4. 验收判据：同图内护柱与花坛墙的**砖块像素尺寸应一致**（当前差 ~2.3 倍），
   用 `target/moscore.py` 式的边缘间距量一遍，别只靠眼睛；
5. 闸门全套：`cargo build` 0 警告 · `cargo test --release` 全绿 ·

### 22.4e ✅ 定案：砖尺度缺陷由**代码推导**确认；我的像素测缝工具连错三次，判废

`procedural.rs::marker_skin` 在 UV 0..1 内画 `rows=4` 行砖，
而铁律 B 写明 marker 用**逐面 0..1 模板 UV** ⇒
**砖行高 = 面高 ÷ 4，恒为四条，与物体实际尺寸无关**。
边界围墙露出地面 2.35m（`city.rs:1475`）⇒ 砖行 **≈0.59m**；
取证图里墙身数到的是**约 4~5 道横带**，与 0.59m 一致，
与"真实砌块 ~0.20m（该有约 12 行）"矛盾。**⇒ §22.4b 成立，修复配方（§22.4b）有效。**

🔴 **同时判废一个我自己造的工具（本轮第三次同错）**：
`target/seam_measure.py` 用"亮度局部极小"找砂浆横缝，在同一面墙上量出
**0.043m / 0.050m（45~53 行）**——既不匹配缺陷预测也不匹配正确预测。
根因：`marker_skin` 内含**骨料双频颗粒噪 + 防色带 dither**（`u*22`、`u*90`、`u*128`），
其幅度足以在每个像素附近制造局部极小 ⇒ **该探针测的是噪声纹理，不是砖缝**。
同族错误本轮已犯三次（`brick_pitch.py` 硬编码错条带、`brick_ab.py` 跨裁剪套条带、
本工具把噪声当缝）。
**⇒ 想量"周期性结构"，用 FFT/自相关找主峰并核对峰值周期是否匹配预测，
而不是数局部极小**；数极小只在一个干净阶梯信号上有效，本场景不成立。

**结论与后续**：缺陷确认、配方确认、修复**仍未落地**——
因为我能证明"缺陷在"，却**还没有一个能证明"修好了"的可靠度量**
（上一个 A/B 用的正是这个已判废的测缝法，所以那次"0.25→0.28 无变化"
**同样不可采信**，它既不能证明修好也不能证明没修好）。
下一轮：按 §22.4b 配方实现，验收改用**FFT 主峰周期**——
修复前围墙应出现 ~0.59m 周期的强峰，修复后应移到 ~0.20m。

### 22.4f ✅ 单面大围墙实测：缺陷**定量确认**，但上一条推荐的 FFT 判据要打折

按 §22.4d 修正机位拍到**单个箱体、露出地面 2.35m** 的边界围墙

**读法**：
* ✅ **缺陷预测命中**：k=4 的周期 **0.570m 与"面高 ÷ 4"逐位相等**，

⚠️ **但 FFT 作为"验收判据"必须打折，别照单执行**：
能量被 k=1/k=2（合计 **67%**）的**残余光照梯度**主导，
缺陷峰 k=4 只占 **3.7%**，与 k=5/k=7（0.39%/0.35%，纯噪声量级）**没有量级差**。

⇒ **修复后若 k=4 消失、k=11 出现，但份额仍在 4% 上下，这个 FFT 判不了**；
   届时的可靠判据是**肉眼数围墙横带行数（4 → 约 12，3 倍差）**，

### 22.8 关闭 §22.3 的残留风险：屏幕锚定的 PCF 抖动**量过了，不到 1 个灰阶 ⇒ 不改代码**

§22.3 修阴影棋盘格时留了一条自我挂账：旋转抽头核的角度取
`fract(sin(dot(floor(input.position.xy), …)))`，**锚在屏幕像素上**
⇒ 相机移动时同一个世界点会换到别的像素、拿到别的角度 ⇒ 怀疑"细噪随屏幕游动"。
挂账时写的是 remedy = 改成按量化世界坐标哈希。本轮**先量，再决定改不改**——
结论是**不改**，理由如下。

**为什么不能"看一眼图"判定**：游动只在相机移动时出现，单帧看不出来；
而"两帧对不齐"这件事本身有太强的混淆项（地面是被强烈前缩的平面，
一个整数平移根本不是两帧之间的真实映射）。所以必须做**同深度对照**。

**实验设计**（`RV3D_SHADOW_SKIP_DYNAMIC=1` 去掉 NPC 影子这个混淆源）：
两架相机 `fly:12.0,1.0,12.0:45,8` 与 `fly:12.283,1.0,11.717:45,8`
——**朝向与俯仰完全相同，只沿屏幕右向平移 0.4m**。
这样同一个世界点的 `world_pos → shadow_uv`、`frag_depth`、屏幕导数全不变，
唯一变的是它落在哪个像素上 ⇒ 两帧各自整数对齐后的残差，就是"随屏幕变"的部分。

**对照**：受光地面上 `shadow_factor` 恒为 1，9 个抽头取什么角度都一样
⇒ 那里的残差是**纯对齐误差**；阴影地面的残差 = 同样的对齐误差 **+ 游动**。
同一条深度带内两者相减才是 PCF 的贡献（`target/swim_control.py`）：

```
y=640-800  阴影 ratio=0.332 (n=47)   受光 ratio=0.235 (n=24)   超出 = +0.097
y=800-960  阴影 ratio=0.524 (n=7)    受光 ratio=0.492 (n=81)   超出 = +0.032
```

`ratio` 是"残差 RMS ÷ 该窗自身标准差"。换算成灰阶：
y=640 带平均 std 9.5 ⇒ 超出 ≈ **0.92/255**；y=800 带 std 4.45 ⇒ ≈ **0.14/255**。
再按真实移动幅度折算：玩家横移 2m/s、60fps ⇒ 每帧 3.3cm，是本实验 0.4m 的 1/12
⇒ **每帧游动 ≲0.08 个灰阶**。

**⇒ 决定：不改。** 用一次未经验证的着色器改动（把角度锚到世界坐标，
在竖直面/球面上哈希退化方式不同，有把 §22.3 的马赛克换回来的风险）
去换一条实测不足 1 灰阶、每帧不足 0.1 灰阶的收益，不划算。
挂账到此关闭，**代码保持原样**。

🔴 **本轮在这条上先走错了一次判据，记下来**：我第一版探针（`register_probe.py` /
`register2.py`）的逻辑是"屏幕锚定的噪声场在两帧的**同一屏幕位置**应当相同 ⇒
高通后在位移 0 处求相关"。跑出来 HUD 与迷你地图 ncc@0 = **+0.9998**、
地面 ≈ **0.000**——看着像"地面完全没有屏幕锚定内容"，**但这个零是假的**：
被屏幕锚定的只是**核的朝向**，而同一屏幕像素在两帧里落在**不同世界点**上，
抽的中心不同 ⇒ 结果本来就不该相关。
⇒ **一个测不到东西的探针给出"零"，不等于被测对象不存在**；
先问"这个量在原理上能不能被这个实验看到"，再跑它。
（同族错误：§22.4e 判废的 `seam_measure.py`、§22.4f 打折的 FFT——都是工具能出数、
数却不对应问题。）

⚠ 顺带记一条与本次无关但实验里撞见的事实：**HUD 与迷你地图在 9px 高通后
仍有 ncc@0 ≈ 1.0、局部 std 高达 32**——它们是屏幕锚定的强边缘。
以后任何"按高频残差找画面伪影"的探针都必须**先把 HUD 区域排除**，
否则测到的全是 UI。

**下一步**（如果将来有人真要做 temporal accumulation / TAA）：那时这条挂账要重开，
因为 TAA 会把逐帧噪声在时间上平均，锚定方式会直接影响收敛结果的稳定性。

### 22.11 新缺陷（未修，已定量）：PT 参照帧的**曝光随 SPP 变化** ⇒ 它现在不能当烘焙真值

回退 PT 皮肤后我继续追 §22.10 那个 "+19%"，先排掉一个更基础的问题：**两帧 PT 到底可不可比**。
结果撞出一条独立的、可复现的缺陷。

**同机位 `fly:60,1.5,-208:0,4`，只改 PT 参数**（`lum_stats.py`，全局灰度均值）：

| 标签 | `RV3D_PT_SIZE` | `RV3D_PT_SPP` | 全局均值 | p5 / p50 / p95 |
|---|---|---|---|---|
| `ptwall_b`  | 1280 | 64 | **113.88** | 90 / 118 / 125 |
| `ptctl_b`   | 2560 | 64 | **114.10** | 90 / 118 / 125 |
| `ptwall2_b` | 2560 | 16 | **90.72**  | 66 / 93 / 119 |

⇒ **分辨率完全无关**（113.88 vs 114.10，差 **0.2%**，分位数逐个相同）；
⇒ **采样数才是变量**：64 spp → 114，16 spp → 91，**差 +26%**。

**为什么这是缺陷而不是噪声**：噪声是零均值的，采样数从 16 提到 64 只会让画面**更干净**，
不会让它**整体变亮 26%**。这是一个**系统性偏置**——PT 帧被当作光照烘焙的硬件 RT 真值用
（`pt_panorama.glsl` 头注："为光照烘焙提供硬件 RT 真值参照"），
那么"改一个采样数就换一档曝光"直接使它在定量场景下不可用。

**已排除的解释**（都不是）：
- ❌ 两帧之间太阳/时间变了 ⇒ 同一次 `cap_safe` 参数只差两个环境变量，且 64 spp 两档分辨率
  的 p5/p50/p95 **逐个相同**，说明渲染本身高度可复现；
- ❌ 分辨率带来的采样覆盖差异 ⇒ 2560/64 与 1280/64 一致到 0.2%；
- ❌ 截图时机（累积没跑完）⇒ 这个解释**方向是反的**，所以不成立：`acc` 从 0 起、
  第一帧拿到的是 `lum × (1/a)`，而 `a = min(0+SPP, 64)` —— **SPP 越大首帧越暗**
  （64 spp 首帧 `lum/64`，16 spp 首帧 `lum/16`）。若真是"没收敛"，16 spp 那轮应该**更亮**，
  实测却更暗 ⇒ 欠收敛解释不了，方向还相反。
  （另注：两档设置的**每帧采样总量相等**——1280×800×64 与 2560×1600×16 都是 65.5 M 样本/帧，
  所以帧预算也差不多，不存在"某轮明显跑得更少"。）

**下一步该查的具体位置**（我读到这一段的表达式，怀疑它但**没有验证**）：
`pt_panorama.glsl` 末尾的时域累积
```glsl
float win = mix(64.0f, 1.0f, move);
float a = min(acc.a + float(SPP), win);
float alpha = 1.0 / a;
acc = vec4(mix(acc.rgb, lum, alpha), a);
```
`acc` 初值为 0，第一帧得到的是 `lum × (1/a)` 而**不是** `lum`——但这条**方向是反的**
（见上面"已排除"第 3 条），所以累积本身不是好嫌疑；稳态下两轮都是 `a = 64`、
`alpha = 1/64`，不动点理应相同。

**关键形态：这不是一个均匀曝光系数**（看分位数）：
`p5 90→66`、`p50 118→93`、`p95 125→119` —— 暗部掉 27%、中调掉 21%、亮部只掉 5%
⇒ 是**随亮度变化的压缩**，不是 `pc.e.w` 那种整体增益。

**两个还活着的候选（都没验证，别当结论）**：
1. **显示端对"运行均值"做非线性映射**（ACES/sRGB 作用在 `acc.rgb / a` 上）：若某处按
   `acc.rgb` 原值而不是除以已累积样本数来映射，`a` 的增长方式（16 spp 要 4 帧才到 64，
   64 spp 一帧就到）就会变成一个**与亮度相关的偏置**——正好是"暗部掉得多"的形态。
2. **`move` 相关的窗口重置**：`win = mix(64, 1, move)` 与 `if (pc.f.y > 0.5) acc = 0`，
   两轮若 reset 次数不同，稳态的加权历史长度就不同。

**判据（便宜、能一刀切开）**：同一机位**连拍 8 帧**、固定 SPP，看全局均值是否单调收敛到
一个不动点；换 SPP 重复。两个不动点不同 ⇒ 累积/归一化写错；相同 ⇒ 差异来自截图时机，
**本节的"偏置"结论作废，应改记为"PT 需要 N 帧才可用"**。
⚠ 写下这条时我只做了三点对照、**没有连拍**，所以上面全部是待验假设。

⚠ **顺带记一条与本轮无关但已看到的隐患**：`uint pxSeed = uint(gid.y) * 2048u + uint(gid.x);`
**假定宽度 ≤ 2048**。`RV3D_PT_SIZE=2560` 时 `gid.x` 最大 2559 > 2048
⇒ 第 y 行的像素 (x) 与第 y+1 行的 (x−2048) **种子相同**，噪声在行间平移重复。
本轮实测它**不影响均值**（2560/64 与 1280/64 差 0.2%），但它是**相关性**问题不是亮度问题，
我的统计看不见它。要判它，得看 PT 噪声的自相关是否出现 `Δy = ±(2048/宽度)` 的条带。

**为什么本轮不修**：定位到表达式不等于验证了因果；改累积权重会影响 PT 的收敛观感，
需要"连拍看不动点"这类多帧实验，而剩余时间不足以内建完整验证。
**记成缺陷单，带数字和入口，比留一句"PT 好像不太对"有用。**


### 22.11b 🔴 更正 §22.11：**不是**"曝光随 SPP 变"，是"时域累积没收敛就被截断显示"（代码级确认）

§22.11 我把 `RV3D_PT_SPP` 当成了"每帧样本数"。**它不是。** 读代码三处连起来：

1. `renderer.rs:6693` —— `RV3D_PT_SPP` 覆盖的是 `pt_spp_target`，**默认 256，单位是"累积多少帧"**
   （注释原文还写着"调参/快速预览可设小值"，我就是照这句设的 16 和 64）。
2. `renderer.rs:11470` —— `let accumulating = self.pt_frame.get() < self.pt_spp_target;`
   ⇒ 到目标帧数就**停止 dispatch**，画面冻结在当时的累积状态。
3. `pt_panorama.glsl` 末尾 —— 累积是**指数滑动平均**：
   ```glsl
   float win = mix(64.0f, 1.0f, move);          // 静止时窗口 64 帧
   float a = min(acc.a + float(SPP), win);
   float alpha = 1.0 / a;
   acc = vec4(mix(acc.rgb, lum, alpha), a);     // ← EMA，不是求和
   ...
   vec3 outc = acc.rgb / max(acc.a, 1.0);       // ← 却按"求和的样本数"归一化
   ```
   `mix(x, y, 1/a)` 是 EMA，`acc.rgb` 已经是"均值量纲"；再除一次 `acc.a` 是**双重归一化**。
   后果不是稳态错（稳态差一个常数，被 `pc.e.w` 吸收了），而是 **`acc` 从 0 起步的暂态
   被直接显示出来**：按稳态窗口 64 帧估，第 N 帧累积到稳值的 `1 − (63/64)^N`：

   | 目标帧数 | 到达稳值比例 |
   |---|---|
   | 16 | **22.3%** |
   | 64 | **63.5%** |
   | 256（默认） | **98.2%** |

⇒ 我测到的 `16 帧 → 90.72` 与 `64 帧 → 114.10` **正是这个暂态曲线**，
方向、次序、非线性压缩（暗部掉得多）全对得上。
**§22.11 里"已排除欠收敛，因为方向是反的"那条作废**——那个推理建立在
"SPP=每帧样本数"这个错误前提上，前提一错，方向判断跟着反了。

**所以 §22.11 的正确表述是**：
- 缺陷真实存在，但**不是**"改采样数换一档曝光"，而是
  **"PT 在累积暂态期间就被显示，且提前截断会留下与截断点相关的曝光误差"**；
- **默认 256 帧已经到 98.2%**，所以正常路径看不出来；
- 真正的坑是 `renderer.rs:6692` 那句"快速预览可设小值"——**设小值等于改曝光**，
  任何拿 PT 当参照做定量对比的人（今晚的我）都会中招。
  已把这句注释与日志改成正向警告。

🔴 **连带影响 §22.10（PT 砖 +19%）**：那两张 PT 帧拍的是 `SPP=64`（≈64% 稳值）和
`SPP=16`（≈22% 稳值），**都不是默认档**。画面偏暗 ⇒ 砖缝对比度被压掉一截
⇒ `course_count.py` 检测到的缝位置**有可能**因此偏移。
⇒ **§22.10 的 +19% 必须在默认 256 帧下重测才算数**，在此之前它既不能定案为缺陷、
也不能定案为我的测量产物。这条已加进 §22.10 的下一步判据前面。

**方法论（本会话第 7 次同族）**：我又一次**把环境变量的语义当成它的名字**
（`RV3D_PT_SPP` ⇒ "samples per pixel"），然后用这个理解去解释三个测量、
还顺手"排除"了正确答案。
⇒ **读变量名不算读代码**：控制类环境变量的**单位与默认值**必须回到它的解析处

### 22.10b §22.10 的 "+19%" **不能**归给测量产物——对比度假设被我自己否证

§22.11b 之后我手上多了一条新线索：那两张 PT 帧拍在 64 帧 / 16 帧累积，

如果成立，§22.10 的 +19% 就是测量产物，PT 皮肤可以直接合。

**专门量了砖缝信号的幅度**（`band_contrast.py`：墙带按行取均值、9px 平滑、
再减 61px 宽 ramp，剩下的就是横缝调制）：

| 帧 | 累积帧数 | 到稳值 | 带内 p50 | **缝信号 std** | 峰谷差 |
|---|---|---|---|---|---|
| `gate_wall_b`（光栅） | — | — | 99 | **10.73** | 48.98 |
| `ptwall_b`（PT 1280） | 64 | 63.5% | 96 | **12.52** | 64.38 |
| `ptwall2_b`（PT 2560） | 16 | 22.3% | 73 | **10.10** | 54.01 |

⇒ **PT 的缝调制幅度不比光栅低**（12.52 甚至更高，10.10 与 10.73 基本同级）。

### 22.12 新缺陷（代码级确认，待实测）：**烘焙路径 `run_pt_view` 默认只累积 64 帧 ⇒ 出厂就偏暗约 36%**

§22.11b 查出 `RV3D_PT_SPP` 是"累积**帧数**"之后，顺着这条线读到两处此前没人注意的不对称：

| 路径 | 默认累积帧数 | 按 §22.11b 的 EMA 模型到达稳值 |
|---|---|---|

| 离线/烘焙 `run_pt_view`（`renderer.rs:7529`） | **64** | **63.5%** |

⇒ **不设任何环境变量，烘焙参照帧也停在稳值的约 63.5%**（还叠加"双重归一化"那条暂态显示问题）。
PT 在仓库里的定位就是"为光照烘焙提供硬件 RT 真值参照"，
而**它被用于烘焙的那条路径恰恰是没收敛的那条**——实时路径反而更接近收敛。

**证据强度要分清**（别把模型当实测）：
- ✅ **代码事实**：两处默认值 256 / 64，逐字读自 `renderer.rs:6693` 与 `renderer.rs:7529`；
- ✅ **模型**：`1 − (63/64)^N` ⇒ N=64 时 63.5%（§22.11b 已推）；
- ◐ **部分实测**：同机位 16 帧 90.7 / 64 帧 114.1，方向与次序与模型一致；
- ❌ **未做**：默认 256 帧那一档没拍过（今晚外部负载 5247~5304 MiB，超 `cap_safe` 的 3200 门槛）。

**可证伪的预测**（GPU 空闲时一次拍摄即可判）：同一机位，
**不带** `RV3D_PT_SPP` 的全局均值必须**明显高于**带 `=64` 的 114.1（线性上约 1.55 倍，

- 若一样 ⇒ EMA 模型错，§22.11b 与本条一起作废，回到"另有原因"。

抬到 256 会让所有既有烘焙参照整体变亮 ⇒ 必须先确认下游有没有按旧亮度定标的东西，
再决定是"改默认"还是"加偏差校正"。**所以本条只登记，不动手。**

### 22.14 ✅ 已修复：PT 的 marker 盒**整体小了一半**（2026-09-17 改约定时漏改的下游消费者）

§22.13 那条"墙顶天空缝"追到根上了。**纯代码事实**：
- 立方体/球模板是 **±1**（`renderer.rs:102 VERTICES` 逐值可查），
  圆柱是 `r=1、y∈[−0.5,0.5]`；
- `obstacle_model` 写的是 `scale = half ÷ template_half_extent`
  ⇒ **`|model.axis|` 本身就等于真实半尺寸**（模板半幅为 1.0 时）；
- 而 `pt_set_scene_markers` 当年写的是 `let hx = |x_axis| * 0.5;`（三轴一律）。

⇒ **PT 里每个 marker 盒的三个轴都只有真实尺寸的一半**；
唯一"对"的是圆柱的 Y——因为它的模板半幅恰好是 0.5，`* 0.5` 蒙对了。

### 23.7 新发现（**有实证、故意未修**）：水平面用俯视投影 ⇒ 同一根梁的**底面方格网**与**柱身顺砌**是两套砌体系统

**机制**（代码级，确定）：`build.rs` marker 皮肤分支按法线主轴投影——

法线主轴是 Y 的面（顶面**和底面**）被投影成 `world_pos.xz`，

### 判据（免太阳方向假设）

同一台机位几何（`fly:x,20,z-8:180,70`，离地 20m、俯角 70°），以圆心取**四条 90° 弧**
（环带半径 `0.055W..0.10W` 像素，**真弧平均**：每 2° × 每半径取样），比较四侧地面亮度。
真有方向性阴影 ⇒ 某侧显著暗于对侧；不投影 ⇒ 四侧相等。
**并加控制点**：同样几何，圆心换到离最近树/楼 **19.5 m** 的开阔地。

| 圆心 | N | E | S | W | spread | 均值 |
|---|---|---|---|---|---|---|

| 树心 `(-27.5, -69.5)` | 110.34 | 103.49 | 98.86 | 84.25 | **26.09** | 99.23 |

(a) 俯角 70° 下屏幕圆环投到地面是椭圆 ⇒ N/S 与 E/W 世界半径不同这一系统性偏差实测≈0；

⇒ **结论：树冠确实投影。§39 的"集体不投影"对树这一半作废。**

## §23.9 追加：立柱"看起来倾斜"这次用**结构事实**结案，不再靠像素（2026-10-02 17:15）
