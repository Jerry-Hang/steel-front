# 超分 / 帧生成适配路线图（DLSS4 · XeSS3 · FSR4.1 · GSR2 · …）

> 2026-10-11 立。用户目标：**未来要适配 DLSS4 / XeSS3 / FSR4.1 / GSR2 …，引擎一个一个把前置条件补上。**
>
> 🔴 **本文的核心判断**：这些技术在**画质算法上互不相同，但输入契约高度同构**。
> 所以正确做法**不是**"接一个 SDK 改一遍引擎"，而是 ——
> **在引擎里把「时域输入契约」建一次，各家 SDK 作为可插拔后端挂上去。**
> 这也是本文的组织方式：先记**契约**，再记**每家的差异**，最后才是**分阶段路线**。

---

## 0. 一句话：缺的不是超分器，是「时域重投影」这条基础设施

`docs/DLSS-evaluation.md` §3 早在 2026-08 就算过一次，结论对今天仍然成立：

> **逐像素运动矢量** — **完全没有**（`rg 'motion_vector' src/` 无命中）— **最大的一块，
> 等于给渲染器加一条 GBuffer 通道**

2026-10-11 实测复核（本次）：

| 契约要素 | 本仓命中 |
|---|---|
| `motion_vector` / `motionVector` / 着色器侧 `velocity` | **0** |
| `jitter`（着色器与 Rust 侧）| **0** |
| `clipToPrevClip` / `prev_view_proj` | **0** |
| `reprojection` | **0** |

⇒ **本仓没有任何一项时域超分的前置条件。** 这一条不变，接哪家都一样。

## 1. 共同的输入契约（**先在引擎里建这一套，谁都不偏**）

> ⚠️ 下面标「待核实」的，是**各家格式/约定确有差异、必须逐家对照官方文档确认**的项。
> 本仓教训：这类"看起来一样其实不一样"的约定（如 PT 的 `* 0.5` 遗留）是最贵的一类 bug。

### 1.1 必备输入

| # | 输入 | 要求 | 本仓现状 |
|---|---|---|---|
| 1 | **渲染分辨率颜色** | 低分辨率场景色，**不含 UI** | 无"内部渲染分辨率"概念（主 pass 直接渲到交换链）|
| 2 | **深度** | 需给后处理采样的路径；**线性化约定各家不同**（待核实：DLSS 期望 reversed-Z 还是普通？）| 深度只用于深度测试，无采样路径 |
| 3 | **逐像素运动矢量** | **必须排除投影 jitter**；相机运动 + 物体运动；**格式与单位各家不同**（待核实：像素 vs UV、`R16G16_FLOAT` vs `R16G16B16A16_FLOAT`）| **完全没有** |
| 4 | **投影 jitter 偏移** | 当帧的亚像素偏移量（Halton 序列），**必须传给超分器**，且**所有几何用同一 jitter** | **完全没有** |
| 5 | **曝光** | 部分家必需、部分可自动（XeSS 有 `XESS_INIT_FLAG_ENABLE_AUTOEXPOSURE`，可免）| 无 |
| 6 | **历史失效信号** | 相机切换 / 关卡加载 / 传送时要**重置历史**（不重置 ⇒ 鬼影）| 无 |
| 7 | **合成顺序** | **UI/HUD 必须在超分之后合成**（官方明确：超分伪影在 2D 文字上最明显）| ✅ **架构已满足**（HUD 走独立 overlay pass）|

### 1.2 可选输入（画质增强）

| 输入 | 用途 | 谁要 |
|---|---|---|
| **Reactive mask** | 标出"这个像素在动/是动态物体"，抑制鬼影 | DLSS |
| **Transparency mask** | 半透明表面的 MV 修正 | DLSS |
| **光学流** | 帧生成的中间帧推断 | DLSS FG 等（部分由 SDK 自带）|
| **UI mask / HUD-less 颜色** | 帧生成需要**没有 UI 的场景色**去做插值 | 各家的 FG |

### 1.3 帧生成的**额外**要求（比超分多一层）

| 要求 | 说明 |
|---|---|
| **present 模型** | 需要 `VK_KHR_present_wait` / `present_id` 一类的"呈现反馈"，才能做帧节奏控制（待核实各家具体要什么）|
| **延迟控制** | FG 必然增加延迟（本仓已知：GSR1 文档提到"初始实现增加一帧输入延迟"），需要配合 anti-lag / Reflex 一类的机制 |
| **HUD-less 场景色** | 见上表 |

## 2. 各家的差异（**这才是真正要逐家对照的部分**）

| | **DLSS 4** | **XeSS 3** | **FSR 4.1** | **GSR2** |
|---|---|---|---|---|
| 厂商 | NVIDIA | Intel | AMD | Qualcomm |
| 类型 | 时域超分 + FG | 时域超分（+FG）| 时域超分 + FG | **时域超分 + FG** |
| 硬件 | RTX（Tensor Core）| Arc（XMX）/ **DP4a 回退可在任意 GPU 跑** | **FSR4 是 RDNA4 的 ML 版**；FSR1/2/3 开源且跨厂商 | **Adreno**（本机 Adreno 810）|
| 接入形态 | NGX SDK（原生库）| SDK / 原生库 | **开源库（可源码集成）** | **开源（BSD-3）** |
| 本仓可用性 | Windows + RTX ✅ | 待核实（DP4a 回退可能在 5060 上也能跑）| 待核实 FSR4 的硬件门槛 | **Android + Adreno ✅** |
| 官方文档 | [DLSS Programming Guide](https://raw.githubusercontent.com/NVIDIA/DLSS/main/doc/DLSS_Programming_Guide_Release.pdf) | [XeSS-SR Developer Guide 2.0](https://github.com/intel/xess/blob/v2.0.1/doc/XeSS-SR%20Developer%20Guide%202.0%20English.pdf) | [FSR 3.1 集成概览](https://gpuopen.com/presentations/2024/FidelityFX_Super_Resolution_3-1_Release-Overview_and_Integration.pdf) · [FSR3 超分与帧生成手册](https://gpuopen.com/manuals/fidelityfx_sdk/techniques/super-resolution-interpolation/) | [snapdragon-gsr](https://github.com/SnapdragonGameStudios/snapdragon-gsr) |

🔴 **每一家的"第 3 项（运动矢量）"格式与单位、以及"第 2 项（深度）"的线性化约定，
接入前必须逐条对照官方文档确认并写成判据。** 这是最容易"接上了但全是鬼影"的地方。

## 3. 引擎要补的东西（按依赖顺序，不是按厂商）

> **关键：下面的顺序与接哪家无关。** 补完 1~5，任何一家都只是"再加一个后端"。

| 阶段 | 要补什么 | 为什么在最前 | 验收判据 |
|---|---|---|---|
| **① 内部渲染分辨率** | `render_extent` 概念：主 pass 渲到低分辨率离屏图，再升采样到交换链 | 超分器的**输入尺寸**就是它；没有它超分无从谈起 | 见 `docs/android-render-scale-plan.md`（规格+10 处改动点已备）|
| **② 深度采样路径** | 把深度以 `SHADER_READ_ONLY_OPTIMAL` 暴露给后处理 | 超分器要读深度 | 同机位调试视图能画出正确线性深度 |
| **③ 逐像素运动矢量** | **本阶段最大的一块**：为地形实例场 / marker / NPC / 道具 / 枪模**分别**产出 MV（相机运动 + 物体运动 + 动态物体）| 运动矢量是时域超分的**核心输入**，也是帧生成的前提 | 🔴 **必须给"已知位移"的判据**：让相机以已知速度平移/旋转，MV 的期望值可解析算出，逐像素比对（本仓教训 27：先确认测量工具测的是你以为的东西）|
| **④ 投影 jitter** | 每帧子像素偏移，**所有几何用同一 jitter**，并把偏移量传给超分器 | 时域累积需要多帧亚像素采样；**MV 必须排除 jitter** | 静止相机下多帧平均应消除锯齿；`jitter` 值可从日志核对 |
| **⑤ 合成链拆分** | 低分辨率场景 → 超分 → **UI/HUD 之后合成**；PT 分支跳过 | 官方硬要求 | 同机位截图：**HUD 文字边缘保持设备分辨率锐利** |
| **⑥ 后端抽象** | `trait Upscaler`：`DLSS / XeSS / FSR / GSR / 纯 blit` 五个实现，运行时按设备能力选 + **必须有的回退** | 这一步做完，后面接新 SDK = 加一个实现 | 每家的 A/B 都能一键切 |
| **⑦ 注册表与回退** | 能力查询 + 失败回退（**回退必须真的能跑**，不能是"理论上可以"）| 各 SDK 的硬件门槛不同 | 强制走每个回退分支跑一轮，且**判据会红**（教训 46：能红的判据才算判据）|

**帧生成（FG）在 ①~⑦ 之后再立一项**：present 反馈 + 延迟控制 + HUD-less 颜色。

## 4. 政策问题（**需要用户拍板，不是技术问题**）

1. **"不新增第三方依赖"这条硬约束怎么办？**
   - **FSR / GSR 是开源的** ⇒ 可源码集成，**不破约束** ✅
   - **DLSS(NGX) / XeSS 是原生二进制 SDK** ⇒ 破约束。但本仓已有先例：
     Android 目标为 `winit` 的 `android-game-activity` 开过一次**有记账的例外**（见 `AGENTS.md`）。
     建议同样处理：**逐条记账、写清"为什么它是可移植性的一部分"**。
2. **平台矩阵**：Windows（DLSS/XeSS/FSR）、Linux（FSR/XeSS）、Android（GSR）。
   🔴 **"坑不互替"** —— 每家的验收要各自独立，不能互相背书。
3. **不做原生 Metal 后端**（铁律 E）⇒ macOS/iOS 这条线走 MoltenVK，超分器最多只能接开源那两家。

## 5. 明确**不做**的（避免重复讨论）

- **GSR2 现在不做**：它要的输入与 DLSS 同构（见 §1），**前置条件就是 ③④**。
  **⇒ 做完 ③④ 后它自然可做，不必现在单独评估。**
- **不按"厂商"排期**：按 §3 的依赖顺序做。**先做谁的 SDK 不影响先做什么前置条件。**
- **不在没有 ① 的情况下评估任何超分器**：没有内部渲染分辨率，超分器没有东西可补。

## 7. 下一步（可执行的）

**只做阶段 ①**（内部渲染分辨率），因为：
- 它是**所有**超分器共同的前置，也是唯一**不依赖任何 SDK** 就能做的一步
- 它本身就有独立收益（实测 2400×1080 → 23fps，1200×540 → 61~67fps）
- 规格与 10 处改动点已经备好

**做完 ① 之后立刻做 ③（运动矢量）**，因为它最大、且是后面一切的地基。
②④⑤ 可以并行或按需插入。
